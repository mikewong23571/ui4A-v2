# UI4A 产品方向备忘录(北极星)

> **这份文档是什么**:创始人口述 + 讨论沉淀的方向判断,是未来所有 track 的裁判文书——
> 当设计分歧出现时,拿它裁决"这符合方向吗"。
> **它不是什么**:不是 spec、不是 track、不是落地计划、不是需求清单。只记录判断与理由,
> 不记录方案。每条判断尽量配一个真实反例——没有反例的原则,迟早被同样的方式再次违反。
> 与现有文档的关系:`product.md` 是使命与 DONE 定义(不变),`docs/domain-objects.md`
> 是"系统有什么"(清单),本文是"系统要成为什么"(方向);判断一旦约束实现,再落成
> `DECISIONS.md` 条目。

## 一、理念三条

### 1. AI as assistant

AI 在你的处境里帮忙,不在它的世界里表演。准确含义不是"AI 帮你做更多",而是:
**AI 让你对工作保有完整认知,同时只做你明确要点头的部分。**

机械含义:助手价值最高的时刻是 scoped Q&A 与责任点协作,不是自主漫游;机械轨迹
(思考步骤、导航历史)属于审计通道,不属于对话。

反例(2026-08-25 生产):agent 在 meta 平面五步导航循环后甩给用户"检测到无进展导航
循环;当前合同未暴露完成目标所需的可执行能力"——这是操作系统的报错,不是助手的话。

### 2. Native context aware

系统原生知道"共同处境"是什么,用户几乎不需要解释"我在说什么"。关键不是感知更多,
而是**声明更少**:用户的位置、注视的对象、所在的工作线,都是现成的结构化事实。

机械含义:凡是"系统从自然语言猜你在干嘛"的地方都是病;上下文必须来自客户端事实
(clientView/位置/scope 声明),不来自启发式。

反例(2026-08-25 生产):chat 用正则 `hasExplicitMetaIntent` 从动词猜平面,把
"新增一篇文章…介绍操作流程"误判为定义变更,整个回合困死在 meta 平面。修复后平面归属
跟用户位置走,一行猜测不留。

### 3. Scoped context is the most important

有限上下文内,收窄决定质量。终极形态:**AI 看到的和你看到的是同一个东西**,只是它
读得更快。scope 是默认镜头,不是围墙——镜头外靠显式导航到达,且每次到达留痕。

机械含义:不把全量 sitemap/定义全文一次性灌进 prompt;按当前 scope → 当前实体 →
可用动作分层披露;呈现按 intent 裁剪,不做全属性绑定。

反例(2026-08-25 生产日志):一个五步 agent 回合的 prompt 近 300KB(整个 meta
sitemap + 全部定义版本全文),LLM 要在里面捞一个 `next` 动作。

## 二、入口论:同一扇门,两个读者

**AI 的认知需要入口,人的认知也需要入口,而且是同一个入口——这是人机协作的真谛。**

- "界面即合同"在操作层已成立(同一 Siren entity/action/guard,同一裁决器);在认知层
  必须同样成立:人和 AI 从同一份投影进入,而不是各进一扇门。
- **指代可解是协作成立的前提。** "这个""当前""还剩几个"必须对双方解析到同一事实;
  引用可点、可验证。对话质量的上限 = 两个上下文的交集;进同一扇门,交集在入口就是
  全集,之后只随显式、留痕的导航分化。
- **canvas 的根因是"共同注视"。** 它独立存在不是页面划分,是协议:agent 导航 →
  canvas 落面 → clientView 回报 → 下一轮上下文。合同是共读的书,canvas 是两人手指
  同时落在的那一行。双向成立:AI 带路时 canvas 跟着 AI,人接管时 AI 跟 clientView。
- **agent 不需要站点。** agent 消费合同,不消费像素;站点全是为人建的。

## 三、工作形态:三种形态,两个半站

划分轴是"节奏 × 信任姿态";站点数等于形态数,不多不少。

| 形态 | 节奏 | 在里面干嘛 | 信任姿态 |
| --- | --- | --- | --- |
| workstation | 高频/日常 | 推进工作线、批准、追问 AI | 信任投影(投影就是为人组装的) |
| meta | 低频/慎重 | 改规则本身:flow/应用/agent 定义/Draft/激活 | 怀疑即职责(diff、审批、human-only) |
| raw/audit | 按需/临时 | 验证"系统没骗我" | 零信任(未组装的原始合同) |

- **workstation 是家。** 默认落点,AI 助手前置,scope 是工作线。
- **meta 是工具间。** 进入定义层必须显式意图;meta 合同站(`/_meta`)后端已独立,
  前端坐实同样的物理隔离。
- **raw 是验钞灯,不是第三个站。** 当前站点形态(裸合同视图)的价值在"未组装",
  它是镜头不是目的地:降格为随处可达的"查看原始合同"模式。
- 两座显式的桥:workstation →(在 meta 中编辑此定义)→ meta;任意处 →(查看原始
  合同)→ raw 模式。跨站链接保留 scope。

### workstation 不硬编码

界面从使用里长出来,不从部署里发出来——否则"应用即数据"当场破产:每加一个
application 就要写一轮前端。

- 硬编码只到"舞台机械":渲染宿主、auth、chat 框、canvas 壳、action gate、words
  词汇渲染器。这层是剧院的灯架,不构成内容。
- workstation 的内容面全是合同实体的呈现:"在等我"=`inbox`,"在动"=`delegations`,
  工作线=投影。人写词汇和舞台,合同写剧本,助手当导演(按 intent/context 规划
  surface),人当观众兼审查(pin/晋升/否决——sidecar→recipe 晋升通道即为此建)。

## 四、原始用户故事(原点,不是需求)

> 创始人做这套应用想解决的自己的问题。记录于此作为方向校准,不构成开发指南。

**故事 A:特性开发。** 传统过程:查代码库/知识库 → 圈定关联仓库 → 克隆 → coding
agent 调研 → 定方案 → 环境管理(agent 操作环境初步调研,了解现实与需求差距)→
开发 → debug。脑子里想要的形态:编排好整个流程,随时问 AI"当前到哪个 phase、
哪个 task 了"。

**故事 B:CVE 战役。** 漏洞平台扫出一批 CVE → agent 收集情报建库(先不关联修复,
建库本身是资产)→ 结合 CVE × 内部仓库 × 历史情报修复 → 随时问"还剩多少没处理完"。

两个故事共享一个内核:**调研 → 定界 → 改动 → 验证 → 评审 → 修补循环**(CVE 修复与
track bugfix 形状相同);差异不在 flow,在**上下文包**(track 文档/需求/关联仓库 vs
漏洞情报/影响组件/历史修复)。两故事共享实体(仓库注册表),flow 各自独立。

**从故事里长出来的核心概念:工作线(work thread)。** 用户的工作单位不是应用,是
"一件事":一个目标 + 一包上下文(跨 scope 实体)+ 进行中的 flow/run + 待批准项 +
最近事件。它是纯投影,不是新真相;是 scoped context 的真正载体,是首页的主角,也是
AI 上下文的边界。conductor 的 track 目录就是它的人工版。

application 的正确定位:**图书馆,不是书桌。** 它是治理与归属单位(定义归谁、scope
归谁),必要的机器边界,但不该是用户的入口。

## 五、方向性加减法(候选清单,不是承诺)

原则:**减法减的是"暴露",加法加的是"聚合"。** 几乎不动引擎,动机器的可见性。

减法(呈现与披露层):
- 首屏机制词汇(surface 宿主/目录协商/表面 ID)收进"为什么这样展示"抽屉;
- sidecar 控制条降级为不起眼的入口,不占工作台好位置;
- chat 的机械方言(机器日志原文轨迹、机械报错措辞)退出对话面;思考流与
  动作轨迹的可观测性保留(chat 是主入口,活性即信任),呈现为可展开的
  思考流 + 活动语言进度;
- agent 的全量 sitemap 投喂,改分层披露;
- 顶层导航零件表(收件箱/事件流/委托监控)折叠为上下文到达;
- 启发式猜测(平面正则已除;起点词级交集探测是下一个)。

加法(投影与组合,不加新真相):
- "工作线"投影对象;
- "我的事"首页:什么在等我、什么在动、上次停在哪;
- 实体动作的一等按钮,可见标注"人/AI 同权"(同一 exec,同一裁决);
- chat 引用可点,引用→事实→画面的因果链可见;
- scope 的显式声明与常显("你在哪、在看什么"永远在场);
- 呈现按 intent 裁剪,不再全属性绑定。

## 六、施工纪律:不做传统软件

落地阶段最可能的歪法:把方向顺手写成传统软件。判据一句话:

> **这段代码换一个 application 还要不要改?要改,就是传统软件,退回。**

合法的硬编码只有两类:舞台机械(宿主/auth/渲染词汇/action gate——换应用不换)
与引擎内核(fold/裁决——语义层,换应用本该换)。其余一切内容面(页面结构、
动作入口、文案、成员规则)必须由合同/数据/投影驱动。

四个已识别的滑梯(每个 track 评审时对照):
- **页面滑梯**:workstation 首页写成 React 页面 → agent 进不来、recipe 管不了、
  新应用要改码。正解:与渲染一篇文章同一台 presentation 机器;
- **特判滑梯**:`if entity.class === 'post'` 的动作组件。正解:渲染器从合同
  actions 通用生成,每实体类型特判代码出现一行即背叛;
- **文案滑梯**:机械报错改硬编码"友好文案"模板。正解:机械层只产结构化原因
  (数据),人话是 LLM 原生认知——字符串模板冒充智能同样违反 AI-first;
- **规则滑梯**:工作线成员资格写成 `if type === cve …`。正解:声明式、可治理
  的数据(迟早经 meta 定义),引擎只做 fold。

既有同类纪律从 meta 扩展到全域:meta UI 不得硬编码 surface 清单、renderer 按
Siren class 选择——每个 track spec 增加固定评审项:**无每应用/每实体类型特判代码**。

## 七、走歪的诊断(为什么会有这份备忘录)

骨架没歪——事件日志、合同、scope、sidecar、human-only 闸,都是为这三条理念准备的;
歪的是落法:上下文收集做了,收窄没做;scope 作为授权边界做了,作为认知边界没做;
AI 接进了执行循环,但"辅助"的姿态在若干交互面让位给了"自治表演"。

一句话:**把系统从"透明可见的机器"改成"有灯、有门、有当前工作的工作台"——
机器还是那个机器;减法关的是机房的窗,加法开的是工作台的门。**
