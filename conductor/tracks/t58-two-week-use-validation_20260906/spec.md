# T58 Spec

## 1. 目标与默认试用对象

交付一个能在**连续至少14天（336小时）真实使用**中承接目标、持续跟踪、支持目标验收的 UI4A 候选。
期间不需要改 UI4A 产品代码、改行为配置/定义救火，或靠开发者终端/数据库操作让日常工作继续。
默认首位使用者为 Mike，任务为真实开发、调研、验证、评审工作；不验证“所有行业/所有任务”。

成功必须同时满足：任务可达成、状态/责任可信、用户觉得方便、产品冻结稳定。
两个星期是**最后稳定候选的验证窗口**，不是从本 track 创建日算两周，也不是总实施工期承诺。
准备期允许验证、真实试用、重构、编码、UIUX redesign；正式期发现必须修的问题则失败并重新候选/计时。

## 2. 本轮边界与依赖

规划基线 `068f9e66`，T56 有在途代码/测试，T57 待实施；两者完成及 review 后再正式接手。
T58 不重复交付它们已承诺的首页/本线功能，负责用真实任务发现并闭环跨层遗留缺口。

原话、验收标准与结果可用已有业务字段/关联材料/受治理定义承载，不为上述故事另建“目标真相库”。
浏览器是人类首要使用面；外部 Agent/CLI 可以执行已授权的真实工作，但其后台帮助必须计入交互成本，
不能由维护者偷偷补齐产品缺口。人类批准仍由真实人执行，工作流自治验收不替代业务审批或试用评价。

## 4. 准备期允许修改什么

- 实际执行/状态/责任闭环缺口：Web服务适配、纯合同/投影、现有Temporal/Runner与回调的必要修复。
- 反复丢失上下文、错误目标、陈旧证据、输入/回执/恢复障碍。
- T56/T57落地后在真实故事中暴露的UIUX问题，按通用词汇/声明改善，不创建每应用专页。
- 试验所需的最小只读证据导出/检查，复用现有事件/审计API；不建立独立分析平台。
- 必要业务定义、Agent定义、Prompt/Recipe/Policy修整，按原治理合同完成并纳入冻结清单。

每次修改必须先形成 GAP 条目与复现，按 Red→Green→Gate 实施，review 后进入下一轮短试用。
优先解决阻断/错误/误导，再解决重复的高成本操作；装饰性改动不抢占关键闭环。
没有真实故事或试验前风险依据的功能扩张，不在范围内。

## 5. 冻结前必须查清的两个现状

1. D78.4 已记录 thread lifecycle 绕过普通确认门。T58 涉及真实授权/归档/跟踪，冻结前必须复核并
   消除试用所依赖的“声明承诺与执行不符”，默认修复应履行的确认合同，先立DECISIONS再改代码。
   不能仅加UI确认、降低策略或从试用中偷偷删掉该故事来算通过。若现行正式决定已改变，核对新合同与证据。
2. `apps/worker/src/activities/notify.ts` 当前通知实现为事件日志＋收件箱；Web Push/SMTP并非已实现保证。
   首轮必须如实约定触达能力：应用内待办是最低要求，浏览器关闭期间不得宣称已主动送达用户。
   若所选真实任务需要离线提醒，则冻结前交付并验证一个用户本人明确选择的真实通道；否则显式使用返回查看，
   且仍须达到追问/恢复成本门槛。不能拿 `notification-delivered` 事件冒充真实设备/邮件送达证据。

## 6. 成功与不成功

唯一验收口径为 trial-protocol 的 M1–M8。样本不足、未到T0+336h、用户未使用/未评价，均为 INCONCLUSIVE，
不能以自动化等效代行。代码修补/配置救火、重大错误/越权/虚假完成为 FAIL；保留失败窗口，重新修整再开。
允许用户在冻结平台上正常修改**任务产物代码**；若任务仓库就是UI4A，候选实例仍必须保持冻结版本。
一旦把这些修改部署/激活到试用实例，属于换候选并重启计时。

两周通过只证明该版本、该使用者、该任务范围内可用，不承诺永久无缺陷、GA、无人监督审批或普遍生产力提升。
