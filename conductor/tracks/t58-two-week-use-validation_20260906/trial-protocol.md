# T58 连续两周试用协议

## 1. 这次验证到底证明什么

证明一个固定候选在预先登记的真实工作范围内，经过至少336小时连续使用观察，
用户能独立承接、跟踪与验收目标，且无需修补 UI4A 产品。不能把两周内持续修补后某一刻可用写成通过。
所有阈值是本次单用户工程验收的拟定标准，不是行业统计结论；T0前可与使用者明确修订，
T0后不能降低门槛或缩小任务范围以取得PASS。

## 2. 入场与起止时间

T0 前必须同时满足：

1. T56/T57 已交付并review；T58准备期真实短试用、必要修复、自动化/浏览器/模型/执行验收全部完成。
2. 试用者明确愿意参与，具备真实任务与每日轻量反馈条件；来源/授权/目标验收边界明确。
3. 目标实例完成实际发布、运行核验与回滚准备，候选SHA/digest/定义/配置已登记；不能仅本地build后开始。
4. 当前没有阻断试用范围的已知P0/P1，或使目标依赖维护者救援的P2。安全及假成功风险不可“先试两周再说”。
5. 人类review通过冻结清单和候选可用性；代码review agent可检查实现，不能代填使用者意愿或满意度。

开始时记录UTC的 `startedAt=T0`、`earliestEndAt=T0+336h`，并附 Asia/Singapore 可读时间。
不以track创建日期/提交日期、经过14次测试或14条日报替代计时；不得改系统时钟或回填过期证据。
正式观察按D01–D14的连续24小时区间记录；不使用的日期也保留“不使用”及原因。
满336小时只是必要条件。样本/反馈不足为INCONCLUSIVE，允许同一冻结候选继续观察，
但必须报告真实总时长（例如20天），不能回称“两周已通过”。

## 3. 冻结对象与日常允许操作

在 `attempts/<attempt-id>/freeze-manifest.json` 登记：

- UI4A release Git SHA；web/worker/runner及实际使用CLI的版本/OCI digest；来源构建和运行实例身份。
- 参与试用的已激活Application/Flow/Agent Definition版本、Prompt/Recipe/catalog/policy及能力绑定版本。
- 非秘密运行配置指纹，provider endpoint/model标识和预算；身份realm/授权策略版本；数据起点/审计seq。
- 目标环境、已验证功能范围、触达方式、回滚/备份证据、试用者与验收协议版本。
- 凭证只记安全位置或generation引用，不写秘密值，不存密码/token的可攻击哈希。

| 行为                                                               | 是否允许不重启窗口    | 计量方式                                   |
| ------------------------------------------------------------------ | --------------------- | ------------------------------------------ |
| 发起/推进/暂停/继续任务，添加真实材料、正常批准、查询历史          | 是，正常合同使用      | 真实事件与目标记录                         |
| 修改任务产物的代码/文档/测试                                       | 是                    | 与UI4A产品自身明确分开；产物版本可追溯     |
| 日常目标说明、合法澄清、已有个人视图展开/密度/pin                  | 是                    | 仍计用户操作成本；不可当成修补产品的渠道   |
| 正常登录/凭证续期、同权限刷新、既定自动备份/自动恢复、只读健康核查 | 是                    | 记录异常和所需人工时间，不隐藏失败         |
| 只追加试用观察/报告，不影响产品运行                                | 是                    | 属证据，不是业务状态；保留原始记录         |
| UI4A产品源码/镜像/依赖修补、在容器hot edit                         | 否                    | 当前attempt FAIL，修复发布后新T0           |
| 修改行为配置、系统Prompt、策略、定义、共享Recipe来绕过缺陷         | 否，即使没有改.ts文件 | 产品修补，不能称“无代码通过”               |
| 用脚本/SQL/清缓存/重建会话/手工补事件救援某个用户目标              | 否                    | FAIL；正常受支持的用户“重试”与此不同       |
| 因产品或集成故障需要人工重启/修复服务才能完成试用目标              | 否                    | 属开发者救援，即使同一镜像也不满足自助使用 |
| 其他分支开发UI4A新功能但未影响试用实例                             | 是                    | 实例持续固定候选；一旦部署/激活即换候选    |

个人Sidecar/业务字段是正常功能，但若用其隐藏错误、补事实、补提示词或绕开失败动作来完成目标，
按“产品变相修补”处理。日常写业务数据不能成为修补系统行为的例外口袋。
外部模型内部版本不能由UI4A冻结：记录可得版本/异常；若导致功能失败仍按原指标计，不自动剔除失败日。
原始业务数据不重置。试用者不能因为任务仓库恰好是UI4A而把任务产物部署到冻结实例后继续算同一窗口。

## 4. 样本登记与目标达成定义

默认1名真实使用者；至少**8个实际使用日、10个独立真实目标**，其中至少8个在窗口内到期可验收。
任务来自实际需要，至少覆盖：开发/修复、调研/方案、验证/评审三类；至少4个包含真实产物变更或独立验证。
至少3个跨日目标、1次≥48h后恢复、两条真实目标并行重叠，不能用批量生成十条todo充数。

每个目标在首次承接时记录：goalId/threadRel、目标原话、来源/材料、范围、禁止effect、
验收标准、约定到期时间、外部依赖及结果验收人。目标可来自既有工作，无须强制重新建线。
原条件变更通过可追溯用户决定记录，保留旧版本和原因，不偷偷把未达成目标改成较容易的目标。

- **达成**：截止约定时间交付符合入组标准的真实产物/结果，由实际用户确认，能指回证据。
- **不算达成**：Agent说done、工具返回success、通过自己写的测试、工作线completed/archived、
  产生一个“建议下一步”的回答，却未完成用户最初要求的结果。
- **取消/范围变更**：必须有用户在结果已知之前的真实业务原因，保留审计；失败后取消仍计失败。
- **未到期**：单独报告，不计到期率分母；若因此不足8个到期目标，结果INCONCLUSIVE。
- **外部阻碍/用户待批准**：跟踪正确不等于目标达成；到期未完成仍计未达成并分类原因。
  不能事后剔除，不能把产品故障改写为外部阻碍。
- **不支持的目标**：必须在承接前明确边界。若UI4A接受后才发现无法做，记承接失败并纳入账本。
  不要求产品支持无穷任务，但不能通过默认拒绝难任务获得漂亮成功率。

prepare阶段记录至少3个可比真实目标的原有工作方式：人花的协调/验证时间、追状态次数、
重复背景次数。匹配任务类型/复杂度说明，禁止用不同难度任务的时间直接宣称因果提升。

自选样本、小样本和同一用户的学习效应都在最终报告说明；不得把这些阈值推广成市场验证。

## 6. 两周节奏与低负担记录

- D01：真实发起/承接，验证用户独立进入，不安排维护者全程站旁指导。
- D02–D06：实际工作；自然离开/返回、不同目标切换、结果核对。人工问卷每天最多约2分钟。
- D07：中期只读review，检查样本覆盖、manifest与已有失败；不得改配置/定义“优化一下”。
- D08–D13：继续真实目标，补自然缺少的情境；不制造假目标/伪造48h中断。
- D14及T0+336h之后：核对全部M指标、真实用户终评、最终独立review，决定PASS/FAIL/INCONCLUSIVE。

自动导出优先复用日志/合同，只收必要ID、时点和结果；用户反馈不能从模型话术推断。
研究记录成本与产品使用成本分列：前者也要控制，后者不因为“在做研究”就被扣掉。
没有真实使用的日期如实写idle，不要求用户为配合报告创造工作。

长任务执行者须持久化下一检查点/待用户反馈/证据位置。需要定时跟踪时，在实际开窗且已获授权后，
使用可用的正式自动化/调度工具创建或更新检查；无调度能力则明确需要何时恢复执行，
不能口头宣称已在后台监控。只读自动检查不得代替真人使用或静默发送外部消息。
通知默认仅有失败、关键变化或需要用户操作才发出，未改变时不反复打扰。关闭/失败后停用相应检查。
本轮未创建调度、提醒或两周monitor。

## 7. FAIL、修复与重新开始

任一 M1/M3 破坏或必须修改产品才能继续的阻断，立即保留失败证据并停止“通过窗口”的累计。
安全恢复优先；不要为维持冻结而继续危险使用。恢复操作仍按实际授权/runbook，禁止删除失败事件。

1. 当前 attempt 标 FAIL，记录首次发生时点、影响目标、用户成本、已做操作和候选身份。
2. 回准备期建立GAP，复现→最小修复→回归→review；新候选重新发布/验证。
3. 新 attemptId、新manifest、新T0，重新连续≥336h；旧窗口不拼接、不删天、不变成“预热”隐藏。
4. 正式窗口中轻微、无需修补且不影响M指标的外观问题可记为不阻断观察；一旦实际部署修复仍换候选。
5. 满两周有指标不达标则FAIL；缺真实时间/样本/反馈/证据则INCONCLUSIVE。不得自动降门槛。
6. 连续两次正式窗口FAIL，必须向用户报告共因和新的范围/资源判断，不静默无限重启或宣称完成。

## 8. 可直接复制的证据模板

实施时建立 `attempts/<id>/`；仅保留必要脱敏证据，不提交产品数据、源码机密、凭证、完整聊天或完整Playwright报告。
外部业务资料使用用户有权访问的位置引用；trial ledger只保存观察，不成为业务状态写回路径。

### Candidate / Attempt

```text
attemptId:
status: not-started | running | failed | inconclusive | passed
participant:
scopeAndProtocolVersion:
releaseSha / imageDigests / definitions / nonSecretConfig:
startedAtUtc:
earliestEndAtUtc:
actualObservedUntilUtc:
touchpointAndLimit:
readinessReview:
previousAttemptAndFailure:
```

### Goal Ledger

```text
goalId / threadRel / source / startedAt / agreedDueAt:
originalGoal / acceptanceCriteria / prohibitedEffects / dependencies:
criteriaRevisionAndUserReason:
resultReference / verification / userAcceptance / acceptedAt:
outcome: accepted | failed | pending | cancelled-with-evidence
forcedStatusQueries / repeatedContext / activeProductMinutes:
incidentIds / countedInDenominator / reason:
```

### Daily / Incident / Review

```text
dayWindow / actualUserActivity / goalIds / snapshotReference:
naturalReturns: elapsedSeconds + correctGoalStateResponsibility:
easeScore1to7 / verbatimFeedbackReference:
userProductTime / researcherRecordTime:
incident: time + symptom + scope + evidence + intervention + freezeImpact:
nextCheck / pendingHumanInput / operator:
```

最终 `trial-report.md` 列每一attempt、实际时长、分母规则、M1–M8原值/判定、
US覆盖、用户结论、review findings、未解决边界和未来适用范围。只有实际PASS才在 metadata/plan/registry 标完成。
