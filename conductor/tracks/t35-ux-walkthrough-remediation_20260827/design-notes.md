# T35 设计笔记 — 工作线(work thread)如何承载用户的业务目标

> 性质:设计审查记录,非缺陷台账(findings.md 管问题实情)、非 spec(不直接构成
> 验收)。源于 2026-08-27 用户命题:"思考 thread 的业务目标;如何承载用户的业务
> 目标。不是某个实例化之后的业务目标,而是从整个 workstation 的角度、整个应用
> 设计目标的层级审查。" 裁判文书:`conductor/product-vision.md`(§四为主)。

## 一、北极星里,线是什么

vision §四:"用户的工作单位不是应用,是'一件事':一个目标 + 一包上下文(跨 scope
实体)+ 进行中的 flow/run + 待批准项 + 最近事件。它是纯投影,不是新真相;是
scoped context 的真正载体,**是首页的主角**,也是 AI 上下文的边界。conductor 的
track 目录就是它的人工版。"

最后一句是关键对照:一个 conductor track 目录携带 spec(为什么做、做成什么样算
成)、plan(现在到哪、下一步是什么)、findings(路上发现了什么)、evidence(证据)。
**工作线的业务目标,在应用设计层级,就是让人和 AI 在任何时刻都能回答三个问题:**

1. **这是哪件事**(目标句 + 为什么/来源);
2. **现在到哪了**(上次停在哪、什么在跑、什么在等我点头);
3. **下一步该谁做什么**(我的责任点在哪、AI 正在推进什么)。

application 是图书馆,线是书桌(§四)。家的默认阅读单位必须是线,不是机器平面。

## 二、workstation 全局审查:陈列轴错了位

现状(R1 走查,`findings.md` F-11 及首页观察):首页三区并列——在等我(`inbox`)/
在动(`delegations`)/我的工作线(`threads`)。这是**机器平面的陈列轴**(按实体
种类),不是**用户的陈列轴**(按"事")。后果:

1. **活动不归事**:"在动"的委托/运行其实是"某条线在动",但首页看不出哪条线;
   "在等我"的确认卡也不携带所属线——等待与推进都悬浮在"事"之外;
2. **目标出生即失忆**:创建线时填了"目标/目标来源"(T26 投影含 goal),但线详情
   页与首页卡片都不再呈现 goal——用户亲手写下的业务目标,UI 里再没出现过;
3. **线详情是动作堆不是叙述页**(F-11):URN 标题 + 五个等宽按钮 + self 卡;
   T26 已投影的目标/引用/进行中/待批准/事件切片全部缺席;
4. **状态机 ≠ 进展叙述**:"停在「open」"是流程语;"上次停在哪、下一步是什么"
   才是任务语(T33 方向,未落到线卡);
5. **线与处境关系弱**:顶栏可声明工作线,但首页不呈现"我现在坐在哪条线上";
   线之间无主次,书桌隐喻没有落地。

根因不是缺数据——T26 的 ThreadSnapshot 已含 goal/owner/status、四类引用、
进行中、待批准、有界事件。**缺的是投影的"叙述组装"与首页的"主角位"。**

## 三、业务目标的四个承载层(设计判断)

**Layer 1 · 目标即身份。** goal 是线的标题性存在:线详情页 H1 用业务标题、其下
第一行是目标句(来源小字);首页线卡第一句同源。零新真相——纯读 snapshot.goal。

**Layer 2 · 目标即参照系。** "到哪了"只能相对目标叙述:进行中的 run 是"谁在为
这件事跑"、待批准是"这件事在等我点头"、事件切片是"这件事最近发生了什么"。
T26 的显式引用聚合已把这些挂到线上,投影按线叙述即可(规则滑梯红线:成员资格
保持事件显式引用,零 type 分支)。

**Layer 3 · 目标即共同处境。** scope=线(§三):AI 开口即知"我们在办哪件事";
引用包让"这个/那个"可解(§二指代可解);线的认知边界 = 助手上下文边界(§一.3
"AI 看到的和你看到的是同一个东西"在线级成立)。

**Layer 4 · 目标即结案回执。** complete/archive 时线应沉淀"结果一句话 + 关键
证据引用"——conductor track 的 done-report 对应物。事件投影可回放,仍零新真相
(结果句可作为 complete 动作的合同参数/事件 detail,叙述由投影生成)。

## 四、workstation 承载形态(演进方向)

- **A. 首页:从"三区并列"到"书桌 + 书架"。** 当前线(声明中的或最近活跃的)升
  第一屏主角卡:目标句 + 停在哪(任务语)+ 该线在动 + 该线等我;其余线一行一条。
  纯投影重组(聚合虚主体,T30 机器),动作保留合 D47.4,零引擎改动。
- **B. 线详情 = 叙述页**:目标(身份)→ 上下文包(可点引用)→ 进行中(谁在跑)
  → 待批准(等我点头,决策卡一击,T33)→ 最近事件(叙述切片)→ 动作(分组、
  危险分层)。F-11 的修法即此,user-stories **S8** 是其最小实现。
- **C. 陈列轴补链**:在等我/在动条目携带所属线回链(有则显示);机器平面集合
  不删(审计/raw 价值),但家的默认阅读轴让位给线。
- **D. chat 分工不变**:线的"推进"正典在 chat(说人话→助手执行,原话授权),
  线的"责任点"在线卡(一击批准);线页不退回表单堆(T33 已定)。
- **E. AI 上下文边界 = 当前线**:assistant 在线内 scoped Q&A,跨线靠显式导航
  留痕(§一.2 上下文来自客户端事实)。

## 五、与 T35 的关系

- S8(F-11)按 B 的方向修,是 Layer 1+2 的最小落地;
- A(首页书桌化)涉及首页区域构成与聚合声明(T30 口径/声明版本升级),超出
  T35 首轮 scope——**登记为方向项,待 F 轮或另立 track**;
- C/D/E 属后续轮次增量;本笔记作为各轮设计依据,修改须先改文档再改码。

## 六、thread 工作台三栏形态评估(2026-08-28,用户草稿 vs 北极星)

> 用户草稿:"推进某个 thread 的时候,会有一个界面:左侧 pin 住 thread 详情,中间是
> 围绕一系列实体的 canvas,右侧是 chat,可查看 chat 历史;进入 thread 时默认进入
> 共同注视,然后就这个 thread 开展聊天。"

**评估结论:该草稿与北极星高度一致——不是"不违背",而是 §三 workstation 定义的
完整形态被用户独立推导了出来。** 逐条对照:

1. **§三 workstation 是家,AI 助手前置,scope 是工作线**——三栏的右栏(chat)
   就是"助手前置"的实体化;进线即声明 scope=线,是 §三 的原文要求。
2. **§二 共同注视协议**——中栏 canvas 不是 thread 的静态附件,而是共读面:chat
   带路时 canvas 跟着 AI,人接管时 AI 跟 clientView;三栏恰是"两个上下文进同一
   扇门"的空间布局。进线 = 声明 thread + canvas 落面 + chat 上下文绑定,三件事
   **在机制层已经存在**(withThreadTarget URL 声明/presence focus/chat 消费
   situation;T26 D44 的 context 类引用挂线),缺的只是"一次点击全部发生且被看见"。
3. **§四 工作线承载**——左栏 pin 的"thread 详情"即本笔记 §三 的叙述页
   (Layer 1+2:目标身份+进展参照系),数据全部来自 T26 ThreadSnapshot,零新真相。
4. **§六 施工纪律对照**:三栏**不得**是硬编码 React 页——必须是 T30 组合机器的
   产物(区域×intent×聚合虚主体:线轨=聚合虚主体,canvas=注视区域,chat=aside);
   左栏纯读(T33 读多写少),责任点(待批准决策卡)在线轨一击可达;中栏跟随注视
   协议而非固定内容。

**与既有裁决的关系**: T33 曾把"AI 前置形态"划出 scope——本方向是用户驱动的
scope 演进,成立的前提是按上述纪律用组合声明实现,而非页面滑梯。

**缺口与依赖(即 T35 现有各项的地基地位)**:
- F-23 应用入口区(E-2)= 从"我的事"进线的入口;
- F-11 线叙述页(E-1)= 左栏内容的投影来源;
- F-12 处境芯片(D-7)= 三栏态势可见的人类半边;
- F-22 分栏粘性视口(D-8)= 右栏输入框常驻的布局前提;
- 命名:三栏成立后 canvas 从导航目的地退化为工作台的中栏,F-25 的名实分离自然
  消解(导航只剩 我的事/定义管理/系统)。

**落地裁决(2026-08-28 用户更新)**: ~~另立 track~~ → **并入 T35 当前轨道闭环**。
三栏组装、线内 pin、切线三路径、inline/委托话术(F-08③)全部在 T35 落地;执行序:
E0 蓝框修复 → D-6 导航 → E-1 线叙述(左栏内容) → E-2 应用入口(书桌) →
W 线工作台三栏组装 + pin + 切线 → D-7 处境芯片(切线路径二) → D-8 粘性视口
(右栏前提) → 文案轮 → R3 收口。纪律不变:组合驱动、左栏纯读、注视协议走 situation。

## 七、thread 内 pin 页面与切线设计(2026-08-28,用户问询评估)

> 用户问:"进入某个 thread,我是不是可以 pin 住某些页面?如何切换 thread?"

**Q1 · pin 页面——可以,而且产品已有两个现成榫头:**
1. 画布宿主已支持 `roots` 参数(逗号分隔多 subject,网格布局)——"钉住的页面"=
   把若干 surface 加进本线的 pinned 集,以 roots 网格常驻渲染;
2. 用户级 Sidecar 已有 `retention: pinned` 语义(个人呈现钉住)——钉住集的持久化
   落在用户级 presentation 事件(可回放),零新真相。

**设计边界(D51 纪律,关键)**: pin 是**用户的个人镜头**,不得改写 situation/注视
——注视是"人机共同现在看到什么"(会动,跟随协议),pin 是"我工作时要常驻的锚"
(不动)。二者是互补而非同一物:AI 带路时注视漂移,钉住的面始终在场。pin 集按线
隔离(随线走,不跨线),AI 上下文不消费 pin(钉住纯呈现层)。

交互形态:任何 surface 角落 📌 钉住/取消;线工作台里钉住面以条带或网格常驻;
chat 带路落新面时,钉住区不滚不动。

**Q2 · 切线——三条路径,主次分明:**
1. **正典:我的事**(书桌):所有线一屏可见,点一条进一条——切线的本质是"换一件
   事来做",书桌是唯一自然的位置;
2. **线内:处境芯片**(F-12/D-7):点当前线芯片弹层列出我的线(threads 投影),
   选择即以新 thread 声明导航;「退出工作线」保留为清除声明;
3. **URL 显式**:?thread=<id> 永远规范可用(CLI/headless 正典,§八 CLI 兼容纪律)。

切换语义:thread 声明变更 → 注视随线走(canvas 落新线叙述面)→ chat 上下文随
situation 走;**chat 历史不随线丢**(session 与 thread 是两个维度:T26 只做
context 类引用挂线,会话史在「历史会话」);pin 集按线各自保留。

## 八、"发消息后 thread 能否自托管"——inline/委托两种续跑语义(2026-08-28)

> 用户问:"发送一个消息之后,thread 可以自托管吗?还是切换页面聊天/任务就中断了?"

**机制事实(代码核实)**:chat 有两种提交语义,续跑能力完全不同——

| | 发送(inline) | 委托(delegated) |
|---|---|---|
| 执行宿主 | web 服务进程内 `await runAgent` | Temporal workflow → worker |
| 切页面/关面板 | **不中断**:服务端循环照跑完,轨迹经 chat-turn 事件留痕;回来从事件流恢复进度(B2 停止=仅停展示,实测坐实) | 不中断(本就是无人值守形态) |
| web 进程重启 | **执行中回合丢失**(进程内任务) | 不丢(Temporary 崩溃续跑) |
| 可观测 | 聊天面板思考流 + 事件流 | 「在动」进度轨 + 委托监控 |
| 结果挂线 | presence 指向线时 context 类引用挂线;产物(如建线)按合同效果挂线 | goal 显式,委托本身在「在动」可归线 |

**thread 的正确定位(回答"自托管")**: thread 是**投影/账本,不是进程**——它不执行
任何东西;执行的是 flow 实例/agent run/委托(Temporal 拥有持久执行),thread 负责把
它们的状态聚合叙述出来("进行中")。所以正确问法不是"thread 自托管",而是
"**把活托付给谁**":要无人值守 → 委托(Temporal);要人机协同时看每步 → inline。
两种都跑在线声明的 scope/thread 镜头内。

**UI 缺口**: 上述语义差异(尤其"发送也可能丢于进程重启""委托=无人值守")在界面
零提示——并入 F-08③(委托/发送双提交语义不清)的修复范围:提交控件旁一句语义
说明("发送=在线协同,页面可切;委托=交后台无人值守,进'在动'"),机制不改,话术补齐。

## 九、线工作台左轨的对齐/对比/亲密性评估与信息组织重设计(2026-08-28)

> 用户质询:"信息呈现里面的对齐和对比,还有亲密性体现在哪里?"——针对当前
> 线工作台(W1 三栏)的现场检视。诚实结论:**三原则基本缺位**,根因不是 CSS,
> 是信息组织格式错了——把全宽 detail 面(属性表+整行动作堆)原样塞进窄轨。

### 现状三问(逐条对照截图)

**对齐——局部有,系统性无**:
- 卡内元素统一左对齐(唯一成立的一条);
- 三栏顶边无统一基线:本线标题/共同注视标题/chat 面板三个起面高度;
- 动作按钮溢出卡片右缘——右边缘不对齐任何东西,对齐系统整体失效的直接表现。

**对比——几乎为零**:
- 标题/状态/正文/图例/按钮字号字重颜色同一档,"目标"这个最重要的信息与
  图例视觉同级,扫一眼抓不到重点;
- 5 个动作同款描边灰:完成(推进)/归档(不可逆)/添加涉及对象(中性)无主次;
- 状态"进行中"是最需要一眼可辨的信息,却是斜体弱灰;
- 左轨与中栏视觉语言完全相同,角色差(常驻摘要 vs 当前注视)不可感知。

**亲密性——相关不相邻,无关插中间**:
- "你和助手使用同一合同"图例插在目标与动作之间,把相关内容隔开;
- "添加涉及对象"与材料清单不相邻——操作脱离了它操作的对象;
- 添加/移出(互逆对)、暂停/完成(状态推进)、归档(危险)三组语义不同的
  动作等距挤在一列——同组不靠近,异组不分隔;
- 钉住的 todos 卡与线叙述卡之间无归属视觉(是材料?还是另一个页面?)。

### 信息组织重设计(紧凑密度变体,呈现层机制)

**现状组(标题区)**:
```
 helloworld                    ← 目标 = 卡内 H1(最重:text-base font-semibold)
 [进行中] 停在「open」          ← 状态 chip + 一句话(次重:status 色)
 来源:chat 消息 #m41           ← 来源弱化(最小字号)
```
**材料组(清单区)**:
```
 涉及对象(2)
   ├ todos        已归档  [移出]
   └ v2 定义下...  已归档  [移出]
 [＋ 添加涉及对象]              ← 添加贴清单,点开选择器
```
**动作组(操作区,语义分组+分隔线)**:
```
 推进:  [完成工作线]  [暂停工作线]
 危险:  [归档工作线]                  ← danger outline,与推进组分隔
```
**图例**: 移出内容流,收进卡片角标(?)或线工作台说明抽屉。

### 实现机制(合规性)

- **密度变体 = 呈现层机制**(T24 已有"切换疏密"先例):线工作台左轨以
  `density=compact` 渲染同一份合同投影——detail 词紧凑分支(免属性表,
  身份+状态+resume 行)、动作组紧凑分支(无框 chip 换行+语义分组)、
  member-card 紧凑分支;零实体特判(密度由宿主上下文声明,非实体类型);
- D47.4 不破:actions/links/members 全保留,只是密度与分组变化;
- 三栏顶边基线:统一 `top` 与卡头高度,栏间距定常量。

**归档确认门(F-30)与紧凑密度正交,均已/将落地。**
