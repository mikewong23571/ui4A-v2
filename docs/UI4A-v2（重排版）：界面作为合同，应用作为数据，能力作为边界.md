## 引言：两个锚点

这套架构立在两个锚点上。它们先于一切机制——合同、平面、边界、审批门，都是这两个锚点的推论；下文五部十一层，是把它们逐层展开。

**锚点一：人类与 AI 面对同一套业务流程，共享同一套业务流程知识。**

一个业务流程的知识，在传统软件里至少住在五处：开发者的脑袋、代码（隐式，埋在 handler 与 if 里）、文档（永远滞后）、给 Agent 的 prompt/Skill（第四份手工拷贝）、老员工的肌肉记忆。每一处都在漂移，而 **AI 时代最贵的不是智能，是拷贝之间的同步**——RAG 给 Agent 喂文档，本质是递给它几张过期的复印件。锚点一说：知识只能有一份，两种读者。由此得到全文的设计剃刀：**任何只存在于单一受众通道里的知识，都是漂移的种子**——schema、guard、sitemap、流程序数是唯一的家；文档、prompt、按钮、聊天，都必须是派生的投影。派生物不会漂移，因为它没有自己的生命。

**锚点二：我们不是为了让 AI 更快地写代码构建软件，而是为了让 AI 能够更好地操作软件而写软件。**

一套企业软件的生命周期里，建造是小 N 事件——建一次，缓慢演化；操作是大 N 流——每天成千上万次：审批在跑、报销在走、工单在结。行业的 AI 投资压倒性地指着前者（代码生成工具链，服务的开发者以千万计），这个设计指着后者（可被操作的运行时，服务的知识工作者以亿计）。两个劳动力池差一个数量级，软件生命周期约 95% 的成本也在操作侧。为建造而优化与为操作而优化，长出的是两套完全不同的基础设施：前者要更强的**生成**，后者要合同、约束、审计与确认门。同一波 AI 浪潮，锚点不同，基建分岔——builder 锚点下的累赘（为什么要引擎？直接生成代码不就行了），恰是 operator 锚点下的必需（没有裁决，操作就是灾难）。

这个盲区为什么持续了二十年？三道锁。技术上，**没有合同可接**——流程知识埋在代码里，机器只能在外围辅助（自动补全、智能回复）或绕道截图（脆弱如 RPA），"操作者"这个角色本身从未被触碰。范式上，直接操纵把动作与人手焊死——**UI 越完美（传统意义上），人类绑定越完美**：完美的 UX 是完美的人类绑定。经济上，按席位收费的 SaaS 把人类操作员本身做成了计费单位——AI 只能被设计成"席位增强"，永远不会是"点击替代"，你以为行业没尝试，其实是计费模式在系统性拒绝。

而"更好地操作"的度量，不是墙钟时间，是**认知带宽的乘法**：AI 可以慢，但如果一句话能委托、异常才在场、N 路任务并发推进、没有预定义的任务也能成功——单位人类认知完成的事务量上去了，这才是快。相应地，UX 的至高目标被倒转：从"让点击更容易"到"**让点击不再必要**"——剩下必须由人点的，才是真正需要人的。目标不是零人类操作，是**零强制人类操作**。

两个锚点合并成一句话：

> **我们写软件，是为了让 AI 能和人一起操作这个软件；代码只是这件事的副产品。**

### 从锚点到合同

为什么答案落在"界面"上？因为这里恰好有一个被晾在一边的现成答案：过去三年把模型嵌进应用、让应用围着模型转的默认姿势，是把最难的问题（理解应用、理解流程、理解用户故事）交给最不稳定的部件（模型的临场推理）——而一个成熟应用的 UI，本来就是**开发者对"这个领域该怎么做事"的理解的物化**。向导的每一步顺序、必填字段、特定状态下置灰的按钮，都是被编码的领域知识；HCI 为人类认知局限积累了几十年的这套模式（上下文有限、会犯错、长任务会迷失），Agent 有完全同构的"认知局限"。要让两种读者共享同一份流程知识，最现成的载体就是这份物化：对人，它一直是把领域知识翻译成可操作形式的翻译器；对 Agent，只要结构可读，它就是同一层翻译器。于是 **UI 成为一份双边合同**——应用对人和 Agent 暴露同一份"这个应用允许你做什么、现在进行到哪一步"的表述。

v1 的结论到这里：**界面应该同时成为写给机器的协议**。这份修订从那个终点再走两步——当协议足够诚实（每个动作有 schema，每个约束有求值，每个拒绝有留痕），两件 v1 没敢想的事自然浮现：

1. **应用可以用这份协议描述和编辑自己**。flow 和 schema 本来就是数据；让"改定义"也走同一份合同，应用就获得了在运行中演化的能力。这是**定义平面**。
2. **应用与真实世界的每一次交互可以收口为同一类东西**。入站是合同，出站是 capability，两边回来的都只是被裁决的事件。这是**能力平面**。

于是核心主张升级为：

> **UI4A：界面是应用与所有客户端（人类、Agent）之间的双边合同；定义是应用写给自己的合同；capability 是应用与世界之间的合同。三份合同共用一套语法——带 schema 的实体、带 guard 的动作、可导航的链接。**

## 第一部：为什么是合同（第一至四层）

*v1 的论证层：处境稀缺、解耦、记忆归属、缓存分层——双边合同的四个面。*

### 第一层：为什么不是 CLI，为什么不是 Skill

#### CLI 是资源式的，没有用户故事

CLI 暴露的是"能力"，不是"故事"。`cli create project --template x` 能跑，但它不告诉你：在真实的用户旅程里，这一步之前应先确认什么、之后应检查什么。CLI 参数的组合空间是平坦的，没有"当前在流程第 2 步，所以此刻只有这些参数有意义"这种时序约束；错误是局部的（exit code），而不是流程性的（"你漏了第 1 步，回到那里"）。Agent 面对 CLI，等于要从零推断用户故事——而用户故事恰恰是应用设计里最贵、最难自动化的部分。

#### Skill 是劝导式的，UI4A 是强制式的

Skill（给 Agent 的文字说明书）告诉 Agent"应该先填 A 再填 B"，Agent 仍可能违反；而在 UI4A 里，B 的字段在 A 完成前根本不可交互——**约束被物理化、结构化了**。好的 Agent 接口不应依赖 Agent 读懂长篇说明，而应把正确路径做成最容易走的路径。

#### 处境是最稀缺的东西

- 渐进式披露 ↔ 分层规划；确认对话框 ↔ 高风险动作前的人工 checkpoint；Wizard 分步 ↔ 把长链推理切成可验证的阶段；
- **UI 状态是 Agent 的外置工作记忆**：与其让 Agent 在上下文里维护"我做到哪一步了"，不如让界面本身承载这个状态；
- **任务效率是上下文作用域质量的函数**。Chat 是无差别累积的模拟信号，会漂移；UI 是被结构锚定的数字信号，每次采样都重新校准。Prompt engineering 的全部技巧，本质上都在用自然语言手工重建一个结构化的作用域——**它是没有 UI 时代的穷人的 UI**。

一句话：**CLI 给 Agent 工具，Skill 给 Agent 知识，UI 给 Agent 处境（situatedness）——而长序列任务里，处境恰恰是最稀缺的东西。**

v2 补充一条实测后变得锋利的对比：function-calling / MCP 的 tools 是**全局广播**的——模型每次都看见所有工具，scoping 要靠额外的权限层；UI4A 的 action 是**处境披露**的——能力只有被某个实体的 action 引用才会在那个实体上出现，作用域从超媒体结构中继承，不需要发明（见第五层）。

### 第二层：关键解耦——AI 从"应用的内核"变成"应用的用户"

此前做 AI 应用是 AI-embedded：智能是应用内部的功能，应用与模型紧耦合。UI4A 翻转这个关系：**应用回到应用本身——它有状态、有流程、有约束、有界面；AI 变成站在应用外面的操作者，和人一样，通过界面理解和使用应用。** Assistant 坐在你旁边，而不是住进墙里。

UI 天然是双方都能理解的边界，于是 **UI 成为一份双边合同**：应用对人和 Agent 暴露同一份"这个应用允许你做什么、现在进行到哪一步"的表述。强推论是：**Agent 继承了几十年 HCI 积累的全部设计资产。**

| | AI-embedded | AI-as-assistant（UI4A） |
|---|---|---|
| 流程/状态的所有者 | 散落在编排代码与上下文里 | 明确归应用，UI 状态即真相 |
| 上下文的生产者 | 开发者手工构造 | 应用结构本身自动生成 |
| 模型可替换性 | 差，胶水层深 | 高，助手外置可换 |
| 出错时的审计 | 翻日志和 prompt | 看界面——它本来就给人看 |
| 人的接管 | 需要专门设计 | 免费获得，人机同路径 |

v2 印证：表中"模型可替换性"在实现里是字面事实——**同一个 agent 执行循环，LLM driver 与规则 driver 一键互换**；未配 API key 时自动回退到内置启发式，配了无效 key 时 401 如实呈现在对话里。决策器是插件，循环是协议。

三层分工维持 v1：外置助手（编排层）↔ 应用（流程层）↔ 内嵌 AI（能力层）。v2 把第三层的身份说得更准了：**应用内嵌的单点认知任务，就是第七层的 capability**。还有一个容易混淆的边界在实现里被显式化：助手自己的 LLM 调用（比如悬浮窗里 agent 的大脑）发生在客户端，那是助手的智能，不在边界上；只有**应用自身**需要的智能（发布时自动生成摘要）才成为 capability。客户端智能与能力的区分，就是解耦原则在认知维度的延伸。

### 第三层：记忆的归属——访问记录即真相，聊天记录即视图

**记忆归应用，聊天记录是易耗品。**

默认聊天范式里，chat history 被迫充当任务状态的唯一载体——"我们聊到哪了"和"事情做到哪了"混在同一条消息流里。UI4A 把它拆开：

- 应用侧持有真实状态：操作记录、当前流程位置——结构化、可验证、本身就是真相；
- 每次人工输入 = 一条新 prompt，注入的是**从应用侧重建的上下文**；
- 聊天记录降级为应用状态的一种视图（view），每次从真相源重新渲染，用完可扔。

这在结构上就是事件溯源：操作记录 = append-only 事件日志；当前 UI 状态 = 日志折叠后的物化状态；喂给助手的"chat history" = 日志的定制投影。事件溯源的好处全部继承：可审计、可回放（换一个模型用同一份日志重建上下文）、可分叉。

**chat history 是助手对历史的转述，访问记录是历史本身。**

v2 印证：实现即事件溯源——引擎侧一份 append-only 日志（`db.edn`），**拒绝的动作同样留痕**；聊天 session 存在浏览器 localStorage，是纯投影，清掉无损。而实测中"拒绝入日志"意外成为 agent 的资源：被拒动作带着引擎给出的原因回到轨迹，成为下一步决策的上下文（见第五层）。

两个 v1 已列出的问题维持：日志 ≠ 意图（双通道投影：事实轨迹 + 意图注记）；投影本身是新的工程层。

### 第四层：缓存工程——Sitemap 作为稳定前缀

可变上下文与推理缓存（KV cache / prompt caching）原理相冲突：缓存要求前缀逐 token 稳定，prune 是反向操作。正确的问题不是"要不要 prune"，而是"如何把 prune 的缓存代价降到最小"。解法是按**变化频率**分层：

```
[应用 sitemap]      ← 版本级变化，跨会话、跨用户命中
[任务/流程定义]     ← 任务级变化，阶段性重生成
[状态投影]          ← 会话级变化，append-only
[当前人工输入]      ← 每轮都变，永远在最后
```

UI4A 的 sitemap 不是 URL 清单，是**应用交互拓扑的完整声明**：界面清单、流程图（用户故事的机器可读形态）、迁移规则、每节点的 action schema、语义锚点。慢层为快层提供压缩编码——访问记录只引用节点 ID，不必重复描述界面。

| | 静态层（sitemap） | 动态层（运行时状态） |
|---|---|---|
| 空间 | 流程拓扑：应用里**能**走到哪 | 当前状态：现在**在**哪 |
| 动作 | action schema：每节点**能**做什么 | 合法动作集：此刻**允许**做什么 |
| 时间 | 用户故事模板：事情**应该**怎么发展 | 访问记录投影：事情**实际**怎么发展 |

这几乎就是导航系统：离线地图包 + 实时 GPS 定位。生态意义上，sitemap 可以走标准化路线（`/.well-known/ui4a.json`）——应用接入 Agent 生态的成本，从"为每个助手厂商定制集成"降为"发布一份自己本来就知道的结构声明"。

v2 印证与推进：实现里 sitemap **从状态机自动推导**——v1 担心的"sitemap 需要平行维护"被消灭，只剩一份真相。v2 的定义平面（第六层）将再进一步：sitemap 变成运行时数据，定义激活即重生成，版本号即缓存键——**缓存失效从一个工程难题收缩为一次显式的版本事件**。

## 第二部：已验证的实现（第五层）

*从选型推理到实测证据：全栈实现、端到端记录、调试教给我们的东西。*

### 第五层：实现——从选型推理到实测证据

#### 已验证的骨架

实现是一个 Clojure/ClojureScript 全栈应用（UI4A·CLJ），完整落实了 v1 第五层的选型：

- **真相源是纯 EDN 数据**：流程状态机 + 每节点的字段 schema + action 声明，可 `pr-str` 传输、可版本化、可 diff；
- **引擎在 JVM**：`rel → Siren 实体`（properties / actions / links，guard 求值结果逐项注入）；`exec` 做三层裁决——action 是否声明于当前节点 → guard 谓词 → 字段 schema，非法动作直接拒绝且入日志；
- **谓词经 CLJC 物理共享**：同一份源代码编译进引擎（裁决）与渲染器（实时重估驱动按钮 disabled）。"按钮的 disabled 与 Agent 看到的 guard 不满足是**同一个谓词的两个投影**"——这句话在代码里字面成立；
- **agent 是纯外部 HTTP 消费者**：只用 sitemap / entity / exec 三个端点。每步三种操作：navigate（沿 GET actions 与 links 迁移，含子实体链接）、action（提交引擎裁决）、done。双 driver：LLM（OpenAI 兼容，sitemap 前缀 + 轨迹 + 当前实体构造 prompt）与规则（目标感知启发式，无 key 时兜底）；
- **assistant 是客服插件形态的悬浮窗**：跨页面悬浮，点击展开聊天；用户输入目标，agent 逐步汇报轨迹（导航、执行、拒绝原因、完成）；右上角历史 session 与 LLM 设置。聊天界面就是事件日志的投影层。

端到端实测记录（浏览器 GUI 黑盒）：

| 目标（自然语言） | Agent 实际行为 | 结果 |
|---|---|---|
| "帮我发布一篇文章" | 导航至发布向导，三步填充（按字段 schema），publish | 文章真实落库，计数 2→3 |
| "把 post-welcome 下线" | 经子实体链接直达 `post:post-welcome`，执行 unpublish | 精确下线一篇，其余未受影响 |
| "审核所有待处理评论" | 导航至审核队列，approve 至 pending 清空 | 队列归零 |
| 同一 session 连续多目标 | 追加在同一会话，轨迹连续 | 会话即审计记录 |
| 无效 API key | 请求真实发出，401 进入对话 | 失败也是合同的一部分 |

#### 调试教给我们的：开放的真正难题

这一节是 v1 完全没有的——全部来自实测中真实发生的故障。让 Agent 自由导航，难题不是"能到哪"，而是"**该不该动**"：

1. **目标相关性是分层的**。"下线 post-welcome"曾顺手归档了六篇文章——goal 点名了具体资源时，同名动作作用于别的资源就是误伤。修正后的决策次序：**点名的资源（上下文参数值出现在目标里）> 点名的动作（名字/标题与目标有词级交集）> 与目标相关节点上的流程推进词 > 自由漫游**，且每层都有停止条件。开放没有相关性纪律，就是连带损伤。
2. **完成相对目标定义，不相对流程定义**。向导到达终态曾被当作万能完成条件，导致"下线"目标瞬间"完成"、什么都没做。流程的终点不是目标的终点——`done` 必须由"完成类动作成功过"相对目标判定。
3. **拒绝是数据，不是失败**。被引擎拒绝的动作带着原因回到轨迹：要么终结一条路径（拒绝去重），要么触发字段级自救——direct 被拒后，按 action 声明的字段 schema 填默认值重试。Agent 与引擎之间的反馈回路，比 agent 的聪明程度更重要。
4. **裁决层零改动**。整个调试期 agent 的自由度持续扩大，引擎的三层校验一行未改。**约束物理化的价值被工程过程本身验证：agent 能力的迭代与权限系统解耦**——你可以放心地调 autonomous，不用怕推翻 authorized。
5. **作用域从超媒体继承**。对比 function-calling 的全局 tools：能力只有被实体的 action 引用才会在该实体上出现。Scoping 不需要额外的权限层，它是超媒体的免费副产品。
6. **事后自省：demo 制度化了"随便填一个"**。`fill-defaults`——agent 遇到不知道的字段就塞默认值或选第一个选项——正是第九层要拆掉的反模式：标题与正文是价值载体字段，本该是"AI 起草三个选项 + 人类选择"，而不是五十遍"Agent 按流程图推进"。guard 校验得了形式（≥200 字通过），校验不了价值；那次演示证明的是机器没错，装进机器的是错误的字段语义。同病根的还有目标相关性打平时的硬猜——归档六篇的教训：**该问的时候在猜**，而问的机制（引出门）当时还不存在。

#### 表达力的实测边界

状态机 + schema 在原型里吃下了：四步向导、审核队列、资源 CRUD、文章生命周期、跨流程自由导航。仍未触及：自由画布（设计工具、白板）、多人实时协作。v1 的推断部分成立——流程密集型应用确实是它的主场。

## 第三部：两个新平面（第六、七层）

*定义平面：应用编辑自己。能力平面：应用触碰世界。目前是粉笔，图纸在附录 A。*

### 第六层：定义平面——应用编辑自己

#### meta application：定义即数据，编辑走同一合同

一个应用由三层构成：**内核**（解释器）、**定义**（结构数据）、**实例**（业务数据）。普通应用里"定义"是源码，改定义 = 改代码重新部署。meta application 把"定义"降格为**应用自己可以通过自己的接口读写的运行时数据**——扩展应用本身，成为应用的一个操作。

三个必要条件：定义是数据（已成立）；编辑定义的界面用**同一份合同**（不是特权管理后台，而是同样的 sitemap/entity/exec）；存在一个固定的解释内核。

这个想法不新——Salesforce 把 Metadata API 与业务 API 拆成两套端点，k8s 让"注册新资源类型"本身就是一次 API 调用，Smalltalk/Emacs 是自修改环境的祖师爷。但它们都有同一个历史包袱：**人类不想通过表单编辑 schema，太乏味了**。UI4A 恰好补上这块：Agent 是史上最好的 meta 客户端——它不觉得"通过 meta flow 定义一个新动作"乏味，它觉得这就是母语。

完整的故事：

> 用户说"我要收藏功能" → agent 操作 meta flow（定义字段 → 定义动作 → 挂 guard）→ 引擎校验定义 → 激活 → 新 UI 自动渲染（渲染器本来就 schema 驱动）→ **agent 的 sitemap 前缀自动包含新能力，无需改任何 prompt** → agent 立刻用新动作收藏一篇文章，全程入事件日志。

#### `_meta`：独立的站点

meta 端点与业务端点不糅合。meta 由 `_meta` 前缀暴露，**相当于一个独立的 site，提供自己的 sitemap**（`/_meta/.well-known/ui4a.json`、`/_meta/api/entity`、`/_meta/api/exec`），自己的 rel 空间、自己的实体模型：

- **可写的定义实体**：`flow:<name>`（节点/边作为子实体——流程定义本身以超媒体呈现）、`definition-version`、`activation-request`。定义的生命周期（draft → validated → active → deprecated）本身就是一个 flow——meta flow；
- **只读的注册表实体**：guards（已注册谓词 + 表达式语法）、effects 词汇表、投影模板、capability 目录（外环第四张表，见第七层）。

关键的是"独立"的精确含义：**独立的是 HTTP 面，不是进程**。`_meta` 路由进同一个引擎、同一个 atom、同一条事件日志（类型区分业务事件与定义事件）。这样定义激活与在途状态迁移共享同一次线性化提交，"激活校验时该节点没有实例、提交时有了"的竞态物理上不可能。

两个站点之间的耦合被压到最小：业务实体的 links 里可以出现 `_meta` 的完整路径 href——现有的 agent 客户端**零改动**就能跨站（它只知道 href，不知道"站点"这个概念）；同时业务站的导航枚举排除 `_meta` 前缀——业务 agent 不该顺路漫游进定义层，进入必须显式意图。权限不对称在挂载点收口：meta exec 是更严的 actor 类 + 审批 guard，鉴权、限流、审计一个句柄全收。实体目录、schema 与操作的完整规格，见附录 A。

#### 内核：解释器 + 注册表——形状从何而来

meta 化没有消灭代码，而是把代码压缩进更小更稳的核心。最终形态：应用里的每样东西要么是**数据**（流程、字段、投影、资源类型、在途实例），要么是**注册表里的具名条目**——代码，但被数据按名字引用。

注册表的数目与分工不是随意选择，可以从协议本身推导。内环协议只有三个动词，每个动词在内核里投下一张注册表的影子：

| 协议动词 | 问的问题 | 内核注册表 |
|---|---|---|
| 呈现（GET entity） | 状态长什么样 | 投影 |
| 裁决（guard 求值） | 此刻允许吗 | 谓词 |
| 迁移（effect 执行） | 状态怎么变 | 效果 |

第四个动词"触达"（capability）在边界上，对应外环的 capability 目录——它登记的不是确定性核内的行为，而是通向非确定性的门，与内环三表不同类。**内核的形状是协议的镜像：动词决定了词汇表。** 最后一层断言仍然存在——"协议为什么只有这些动词"没有推导者（固定点无法自我推导），这是全文承认的最后一个不动者。

**注册表是内核的词汇表，数据是用词汇说出的话。**

自指在这里触底：meta 站可以只读地描述自己的 schema——内核可读不可写，内核以下皆可写。完全自指不可能（总有一个解释器不能解释它自己），但内核会越来越小、越来越稳。

#### 在途状态：定义变更下的实例迁移

flow 定义改了，停在旧节点上的 session 是什么？三个手段组合：

1. **实例盖版本戳**：每个实例记录出生时的定义版本，在途实例按旧版本走完生命周期（长流程引擎的标准做法）；
2. **定义只增不删**：废弃代替删除，protobuf 式演进，旧节点永远可达；
3. **激活前校验是一个读库的 guard**："被删节点上没有存活实例"——和 `is-pending`、`no-posts-using` 同一种机制。**非法动作被拒绝且留痕，非法定义也应被拒绝且留痕**：同一条原则向上一层的投影，同一套裁决机器的复用。

还有一个工程细节是白拿的：引擎是单 atom，所有变更串行提交。定义激活和在途迁移如果都过这个 atom，就不会出现"激活校验时没实例、提交时有"的竞态——**定义层和实例层共享同一次线性化**。

#### 需求溯源：一条日志，两个层面

事件日志同时记对象层的状态迁移和 meta 层的定义变更。于是能回答以前回答不了的问题："这篇文章为什么是 archived？"→ 因为它在 v3 定义下处于 published，而 archive 这条边是 v2 时代 agent 通过 meta flow 加上的。**需求、定义、状态共用一条因果链**——这可能是 meta application 最值钱的副产品。

### 第七层：能力平面——capability 作为与真实世界的边界

#### 边界是双向的，真实世界只有提议权

真实世界与应用的交互只有两个方向：

- **入站**：真实世界的参与者（人类、Agent）作为**客户端**，按合同调用进来——每次调用被三层裁决，非法的拒绝且留痕；
- **出站**：应用需要真实世界（LLM、外部 API、时钟）时，通过 **capability** 调出去——每次调用是一次流实例，结果以事件回来。

合并成一句话：**真实世界对应用没有写权限，只有提议权。** 人类填表是提议，Agent 执行动作是提议，LLM 的产出是提议，连时间到点也是提议（tick 事件）。所有提议过同一个裁决器，落同一条日志。**人类不比 GPT 特殊，时钟不比邮件服务特殊。**

这条线买到的：**确定性变成结构保证**——引擎物理上只能通过发出 capability 请求接触外界，日志 + capability 产物 = 完整的重放输入，应用核心是日志的纯函数（事件溯源的理想经常毁于"有人在 handler 中间调了个 API"，边界让它不可发生）；**溯源单点收口**——每一分外部影响都以带类型的事件入日志（哪个能力、哪个版本、内容寻址的产物、过了什么 guard）；**失败语义归位**——外部世界的失败（慢、错、不可用）在边界上统一处理，超时、重试、补偿全是 capability 流上的边。

一个容易漏的边界居民：**时间**。引擎直接读墙钟作元数据无害，但任何依赖时间的逻辑（"48 小时未审核自动通过"）必须是时钟 capability 的 tick 提议，不是后台线程改状态——这是重放确定性的最后一块拼图。

借用纯函数语言的说法：**capability 是这个应用的 IO——你等于把 IO monad 做成了超媒体。** 它不是类型系统里的边界，是有地址、有 schema、可导航、可审计的边界。

#### 如何抽象：能力的主语是工件，不是业务

判断标准只有一个：**描述这个能力时，能不能不出现任何业务名词？**"把 PDF 的表格提取为 table"是能力；"解析发票 PDF"是业务函数穿了能力的马甲。

能力的接口统一为 **`artifact(s) in → artifact out`**，两端声明 schema：

- **工件（artifact）**：file、text、`document/pdf`、table（带类型列的行列结构）、image、embed。工件内容寻址，入日志，业务实体只存引用。**上传是工件获得名字的时刻**——客户端把工件提议进边界，之后所有能力作用于这个地址；
- **三类动词**：**转换**（PDF→text、XLSX→table：形式变，语义不变）、**提取**（OCR、摘要、实体抽取：工件→结构化描述，模型背书的那类）、**效应**（发邮件、调外部 API：出站边界那类）。

schema 参数化是允许的（`table→json:<target-schema>`，schema 是数据）；业务名词参数化不允许（"mode: 发票"是映射漏进了能力层）。

#### 调用即流实例

业务 action 的效果是 `spawn` 一个 capability 流的实例；capability 异步执行；完成以事件落库；业务状态机多一条由完成事件驱动的边。由此：引擎的同步裁决保持确定性（非确定性被隔离在 capability 流的实例里，产出以被裁决的事件回来）；慢和失败有了一等表达（超时边、失败迁移、补偿，全是图上的边）；在途的 job 本身是实体——**用户和 agent 都能看见应用正在思考什么**。

一条铁律：**guard 永远不调 capability**。guard 读快照、必须纯且快；capability 的结果先落成状态，guard 再读状态。

#### 与业务的结合：市场，不是雇佣

业务侧的引用 = capability 引用 + 参数绑定 + **结果映射** + 状态边，全部是定义数据。拿"上传供应商报价 Excel，入库并通知采购"走一遍：upload（工件入库）→ `xlsx→table` → `table→json:<schema>` → **业务映射**（json 字段 → 报价单字段，声明在业务定义里）→ guard 校验 → `notify`（模板是绑定数据）。六步里没有一行代码知道"报价"或"采购"是什么。换一个业务——合同 PDF 提取条款——只换 schema 和映射，能力一个不用新写。

模型背书的能力有特殊的泄漏点：prompt。**"总结这篇博客给读者看"不是能力，"按长度约束总结 text"才是**——业务性措辞作为模板放在绑定数据里，prompt 模板是映射的一种。

防止能力沦为业务附庸的三个结构性机制：

1. **接口只有工件**，业务名词进不了签名——可以作为注册表准入的机械检查；
2. **组合性测试**：新需求先问"现有能力的组合 + 新映射能不能满足"；一个从未被第二个业务引用过的"通用能力"，大概率是伪装的——**复用率是附庸化的体温计**；
3. **生命周期独立**：能力有独立的版本与废弃流，业务引用带版本的能力名；如果能力的每次变更都要同时改某个业务 flow，耦合已经发生——版本化让耦合显形为一次显式升级事件。

业务和能力的关系是市场，不是雇佣：业务拥有语义、状态、流程、裁决——能力永远不该有；能力拥有对世界形态和力量的触达——业务永远不该自己写。`_meta` 的注册表是这场交易的柜台。

#### coding agent capability：把内核边界变成一条管道

写代码可以成为 `_meta` 上一个受治理的能力流：

**generate → validate（跑测试套件）→ sandbox（受限求值，谓词强制纯度：禁 IO）→ approval guard（人类或规则审批）→ activate（热载入注册表，事件留痕）**。

代码产物内容寻址，定义事件引用不可变工件。内核仍然拥有"装载代码"的动作——边界没有消失，只是从"不可能"变成了"需过审"。这本质上是 PR 流程：**coding agent 对应用本身开 PR**。信任锚不是模型可信，是验证管道 + 审批 guard 可信。

它还有个对偶读法：coding agent 不但是被托管的 capability，也是 `_meta` 的客户端——同一个变更，今天是改源码文件，明天是三条 HTTP 调用。文件系统降格为内核的实现细节，Agent 对应用的操作方式从"改代码"变成"走合同"。

## 第四部：人的位置（第八至十层）

*信任线：委托与确认。交互：三扇门与字段语义。渲染：生成式呈现与骨架。人类何时进环、看到什么、如何被呈现。*

### 第八层：权限——委托、确认与渐进信任

v1 把安全与权限列为最可能致命的洞。解法不该是为 Agent 发明一套新权限体系，而是一个反向的判断：**Web 2.0 花了二十年建好的权限基础设施（账号、会话、OAuth scopes、RBAC、审批流）已经足够成熟，缺的只是一个维度**——人类权限回答"谁在操作、允许做什么"，Agent 在这两个问题之前多了一问："**代表谁**"。而 OAuth 连这个都准备好了：Token Exchange（RFC 8693）的 `act` claim 早已声明"签发给 X、代表 Y 行动"。

于是模型是：

- **Principal（委托人）**：用户账号——权限的主体始终是人；
- **Actor（行为者）**：人类会话 | assistant 角色。事件日志同时记录两者：`actor=assistant, principal=user`；
- **权限求值** = 用户角色的 RBAC ∩ 委托范围（这个 assistant 被允许做什么）。

实现里这颗种子已经在：每个事件都带 `actor: "human" | "agent"`。缺的只是把它从审计字段升级为**求值输入**。

#### 确认门：一条 guard，一个实体，一次能力调用

关键业务动作在 assistant 身份下执行时触发确认，以消息通知为载体——这个机制在架构里完全不需要新概念，它是已有原语的组装：

1. **确认门在裁决的 guard 阶段生效**。action 声明携带 `:requires-confirmation`（风险分级，数据）——注意它不是读库的状态谓词，而是**策略标注**：谓词回答"状态允许吗"，标注回答"这个 actor 是否需要委托人确认"。guard 的结果由两种（通过/拒绝）扩为三种：通过、拒绝、**挂起**——动作转入 pending 状态而非被拒绝。这是一次显式的概念伸展，记入设计而非混入（谓词求值保持纯与快，标注不参与求值、只参与分流）；
2. **待确认动作是一个实体**。`confirmation:<id>`，properties 带着原始动作、参数与 Agent 的理由，actions 只有 `approve` / `reject`。**这就是审核队列 n=1 的特例：被审核的是 Agent 的动作，审核员是委托人**——moderation flow 一直是这个机制的业务原型，此处升格为平台机制；
3. **通知是一次 capability 调用**。确认实体经 notification capability 推送到人类的任意信道；聊天里的确认气泡、手机推送、邮件，是**同一个实体的不同渲染器**；
4. **人类的点击是一次提议**。approve 是 `actor=human` 的一次 exec，被裁决、留痕。

```
agent: exec {action: archive, params: {...}}
  → 引擎裁决: guard requires-confirmation → 动作实体化为 pending
  → capability notify: "Assistant 想以你的身份归档《…》，理由: …"
  → human 在任意渲染器上 approve（exec, actor=human, principal=user）
  → 原动作执行。事件留痕：提议者 agent、确认者 human、信道、时间戳
```

链路的每一步都是同一套语法：guard、实体、能力、提议。**权限没有成为第四个平面，它是穿过三个平面的一条线。**

#### 信道分离：确认比执行更可信

确认的载体放在人类的设备上（推送、邮件），带来一个真正的安全属性：**确认信道与执行信道分离**。浏览器里的 Agent 被提示注入攻陷，点不了你手机上的推送。这把 v1 洞里最凶的场景降级：注入攻击从"全面沦陷"变成"被委托范围与确认门限制的**有界损伤**"——被攻陷的 Agent 最多能做不需要确认的事，而那正是你声明过愿意承受的范围。这是 3-D Secure / 交易签名在 Agent 时代的对应物。

#### 风险分级与渐进信任

确认不是开关，是阶梯：

- 只读动作：assistant 身份直接执行，日志留痕（事后审计）；
- 低风险写：执行 + 留痕；
- 高风险写（花钱、不可逆、外发效应）：确认门（事前批准）。

且信任可以演化：同类动作 N 次确认无误后可提升为免确认（scope 提升），用户可随时收回。**委托预算本身是数据**——可以在 `_meta` 定义、在用户设置实体里演进。信任的"慢慢完善"，与 meta application 的演进是同一个哲学在安全维度的投影。

#### 诚实的代价

1. **确认疲劳**：什么都确认，人类会退化成盲目点同意的橡皮章（automation bias）。对策：风险分级、批量确认（"Agent 想做这 5 件事"）、渐进信任把确认留给真正的高危；
2. **超时语义**：pending 确认要能过期——超时边，又是时钟 capability 的 tick 提议；
3. **范围配置的 UX**："允许 assistant 做什么"的界面要好用，这是产品问题不是架构问题，但决定采用率；
4. 读取权限（GET 的 scopes）与执行权限要分开声明。

### 第九层：交互——三扇门、字段语义与澄清器官

第八层解决的是"高危动作谁批准"。但人类进环其实有三个不同的理由，各需一扇门；而字段——合同的最小单位——需要一套语义，说明每个值从哪里来、由谁在乎。这一层把它们补齐。

#### 三扇门，一个介质

| 人类进环的理由 | 门 | 形态 | 粒度 |
|---|---|---|---|
| 风险：可能出错 | 确认门（第八层） | approve / reject | 动作级 |
| 价值：必须创好 | **选择门** | AI 起草 N 个草稿，人类选择、编辑 | 字段级 |
| 模糊：人和 agent 都不清晰 | **引出门** | 对话直到 schema 可满足 | 字段/分叉级 |

三扇门机制同构（pending 实体 + 等待人类提议 + 留痕），共享同一个介质——确认消息、草稿选项、澄清问题，都最好在同一个对话面到达。**选择门可以吸收确认门**：一次发布的全部价值字段刚被人类选择过，动作级确认按策略可豁免——门开在判断发生的地方，摩擦留在门外。

选择门改变的是创作经济学：**从面对空白页，到做选择题**。人类选择与编辑的认知成本远低于从零创作——这是对创作者真实、诚实的加速，不假装人类不需要在场。AI 不是替人写，是把人从生成挪到判断，而判断恰恰是人类便宜且愉快的部分。

#### 字段语义轴：值从哪里来

字段按"谁在乎这个值"分四种语义，按"值如何获得"排成交互成本阶梯：

| 语义 | 谁在乎 | 来源机制 | 人类成本 |
|---|---|---|---|
| 组织标准 | 没人——组织早答过了 | **默认**（静态 / 上下文 / 策略路由 / 词汇别名） | 零 |
| 意图 | 委托人，一句会说 | 显式提供 | 低 |
| 价值载体 | 价值就是字段本身 | **起草 + 选择**（AI 起草，人选） | 低-中 |
| 模糊 | 人和 agent 都不知道 | **引出**（chat） | 高 |

由此立两条铁律。

其一，**事实永不发明**。一个需要 agent 去"填"的 IP 字段是 schema 设计错误——IP 是事实，只能被默认（组织惯例）、查找（IPAM 查询）、效果产出（"分配 IP"是 capability 的效果，字段持有产出引用）或引出（"你倾向哪个子网？"），唯独不能被编造。"agent 猜"只对价值载体字段合法，且要过选择门。

其二，**默认值在引擎侧解析**。exec 时对未指定字段应用 schema 声明的默认值，guard 对最终参数求值，日志记录每个参数的出处——`{value: "cn-beijing", source: default}` 与 `{source: intent}` 分得开，确认消息因此能渲染"哪些是你说的、哪些是被假设的"，人类批准的是一份透明清单。改默认值是高杠杆变更（此后所有"没说"全部改道），走 meta 的激活门；永远不要用"第一个选项"当默认——静默的错误就是这样溜进来的。

交互成本阶梯（默认 < 意图 < 选择 < 引出）给出 schema 设计纪律：**为每个字段选够用的最便宜交互**。反面有两种：把一切做成 chat（对话式表单，比表单还累），把一切做成默认（替人决定他该决定的事）。

#### 澄清器官：内嵌，不是 assistant

引出门的执行者不是外置 assistant——**assistant 是人的代理，忠诚于目标；clarify 是应用的器官，忠诚于流程收敛**：必须收敛到 schema 满足，必须扎根在合同上。v1 第二层"应用内嵌 AI 作为器官"在此落地为具体的解剖结构。它是一个带类型的 capability：

```
capability: clarify
输入工件: {fields: [字段schema], context: 实体快照, 约束: guard 求值}
输出工件: {values: {字段: 值}}          ← schema 校验通过才准出
执行者:   高级 AI × principal
终止条件: schema 满足 | max-turns | timeout
```

关键性质：**chat 不是聊天，是一个函数**——输入悬挂的字段，输出满足 schema 的值，对话只是求值过程。澄清问题应扎根合同（选项来自 schema 的 options，约束来自 guard 求值），chat 由此成为人类探索动作空间的方式，而不只是表达意图的方式。

触发是双层的：实体投影携带字段语义，守规矩的 agent 看到 elicitation 字段直接开澄清、不提交垃圾（主动）；提交后校验失败且字段声明 `:on-invalid :clarify`，引擎把拒绝转换为澄清 session（被动兜底）。拒绝回流也按失败形状路由：**状态型失败（非法迁移）回 agent，意图型失败（缺 intent 字段）路由给人**。澄清的对话记录挂在决策点上，就是 v1 洞清单"意图缺口"的机械解：日志记"发生了什么"，transcript 记"怎么聊清楚的"——出处记作 `elicited:session-N`，意图注记不再缺一层。

#### runner 阶梯与 AI-optional 总原则

clarify 的合同固定，智能可插拔：`:form`（渲染成表单/推送按钮，零智能，永远可用）、`:rule`（规则生成问题与选项）、`:ai`（高级模型对话）。**最哑的澄清就是传统表单本身**——表单从来是一种退化态的澄清，AI 改善的是问的质量（带上下文的选项、权衡的解释、把人聊清楚），不是问的机制（pending 实体 + schema + 回流裁决）。模型分层跟着注意力分层：便宜的经济模型跑过程（driver 每步决策），贵的高级模型只出现在人类在场的地方（按 session 付费）。

由此浮出整套架构的总原则：**机械层必须在零智能时完整工作；智能层只改善体验，不承担正确性。** AI 在系统里恰好出现三处，各有哑兜底——driver（兜底 rule driver，已验证）、clarify runner（兜底表单）、价值字段起草（兜底空页人自己写）。引擎、guard、pending 实体、裁决，全部零依赖模型。**这是一个 AI-optional 的设计，不是 AI-dependent 的设计**——AI 是可摘除的器官，不是脊柱；模型换代、断供、组织禁用，系统降级运转，不崩。

信任线在这里又长出一节：**澄清应答权本身可以再委托**——"他总是选子网 A，这类别问了"，例行分叉由 assistant 代答，真分叉升级到人。动作可委托、确认可委托、澄清也可委托，每一级都有账本与收回。

#### 委托即流程实体，与 plan-exec

要兑现"认知带宽乘法"，还差两块建筑：

**其一，委托本身要成为一等流程实体**（goal → running → waiting-confirmation → done / failed，轨迹是子实体）。N 个委托 = N 个实体并行——**裁决器就是并发控制**：guard 对当下状态求值，两个 agent 抢同一条评论，一个成功一个拿到 is-pending 失败，留痕、可自愈，并发安全是合同的副产品。人类管理"agent 舰队" = 操作又一个 UI4A 应用（委托队列、批量批准、催办、取消）——管理 N 个 agent 的认知成本不是一个聊天窗 × N，是一个队列页。v1 的"UI 状态是外置工作记忆"在 agent 自己身上闭合：agent 崩了、断了、换了，委托实体还在，**换一个 agent 从实体续跑**。聊天窗由此升格为**人类注意力的唯一入口**——目标形成、途中澄清、确认批准、草稿选择，全部作为对话到达。

**其二，plan-exec**。合同把 agent 按在 UI 节奏上：一步一往返，六步流程付六次决策延迟。补一个动词：agent 一次决策输出整段计划，引擎在**一次事务里逐步模拟**——每步仍对演化中的真实状态做完整三层裁决，通过则提交，被拒则分步报告。不是"信任计划"，是"批量裁决计划"。操作节奏从 UI 步调升到引擎步调，裁决权一寸不让。规则 driver 本质上就是一段编译好的计划——plan-exec 让 LLM driver 也能接近这个速度。

### 第十层：渲染——形式可生成，骨架与 BIOS 不可

第九层解决"人类何时进环"；这一层解决"人类看到什么"。传统答案是开发者提前建造页面。这里的答案分三段：**注意力的内容按需生成，注意力的基础设施预建，自修改系统的修理工具烧录。**

#### 生成式渲染：AI 选形式，永不选数据

界面坍缩为一个悬浮窗——左边对话，右边画布。没有预建的实体页面；你说关注什么，AI 从组件词汇表（表格、表单、时间线、diff、卡片组、流程图——投影注册表的呈现侧对应物）里**选**一个组件，发出绑定说明，本地渲染器从实体缓存解引用取值：

```
render: {component: "table",
         bind: {rows: "entity:reimbursements.items",
                columns: ["project", "amount", "status"]}}
```

整件事系于一把剃刀：**模型只发引用，不发内容——字面意义上发不出一个数字**。幻觉的最坏结果是排错列、选错图，对照实体一眼可查；数字永远来自实体字段。交互层更硬：**任何可点的按钮必须绑定到已声明 action**——渲染器只接受绑定，合同外的动作无法提交。装样子可以，骗点击不行：注入攻击能污染展示层，穿不透交互层。"渲染图片"仅限静态产物（一张图表）；交互层必须是结构化组件——**选，不是画**。

稳定性设计：**按关注点凝固**——某类关注点首次生成渲染，之后缓存，同一关注点永远同一布局。对话式渲染最大的隐患是肌肉记忆：靠空间记忆导航的高频专家流，稳定界面永远快过重排；凝固保住了锚点，AI 成为首次相遇时的排版师，而不是每次重排的房东。副产品：渲染说明是数据，可寻址、可分享——**"页面"死了，可分享的命名渲染生了**。

赢得三样：数据跟着注意力走（不再菜单考古）；长尾视图开发成本归零（"这个月的报销按项目看看"——没人开发过那个页面，绑定当场就是）；UI 维护从 N 个页面坍缩为一个画布加一个词汇表。A2UI 由此被正确接回：v1 说它"方向相反，做不了真相源"——有合同在下，A2UI 渲染的是**确实是**的，只选择怎么看。

#### 骨架：不能委托给 AI 的五个面

生成式渲染的删除测试——什么不能交给模型现选，四条判据：必须在零智能时可用（开机态）；必须永不遗漏（异常到达面）；必须独立于被审计者（审计通道）；必须是空间记忆的锚点（归位）。过测的五个面：

| 骨架面 | 角色 | 一句话设计 |
|---|---|---|
| **主页** | 零智能态 + 最常看 | **态势简报，不是内容清单**：待我处理的（挂起的确认与澄清）、在飞的（运行中的委托）、刚发生的（最近事件）——对日志与 pending 实体的投影，不引入新真相 |
| **归位** | 空间锚点 | 永远在固定位置的"回主页"——重排一切的对话式界面的唯一钉子 |
| **事件流** | 信任锚 | **渲染路径零 AI**，机械投影，数字直接来自日志——怀疑 AI 时去看的地方，也是自述可核验的地基 |
| **收件箱** | 异常面 | 三扇门的 pending 实体：角标 + 队列，持久不遗漏——推送是瞬时的，收件箱是持久的 |
| **对话 + 画布** | 主角 | 画布默认渲染 = 主页；对话驱动动态渲染；按关注点凝固 |

骨架同时是 assistant 的工作台面：**画布是澄清的上下文**（问题指着屏幕问，对话与渲染共享注意焦点）、**事件流是回执簿**（agent 的自述必须对得上）、**主页是议程**（人和 agent 的优先级基于同一份投影）。

#### `_meta` 的 BIOS：内建 UI，不可委托的修理工具

一个能修改自己的系统，必须有一件不依赖被修改部分的修理工具——**修自己的扳手，不能是自己造的零件**。`_meta` 是应用改写自己的地方，所以它的 UI 不能是 meta 定义的（定义坏了就没界面）、不能是 AI 渲染的（模型不可用时恰恰是你要去 `_meta` 的时候）、不能是扩展提供的（扩展本身是 meta 的产物）。**内建 meta UI 是应用的 BIOS**：随内核发行、不作为定义存在日志里、保留路由不可劫持。

最小内建集对着附录 A 的最小核：**定义查看**（自省不致失明）、**激活队列 + 机械 diff + approve/reject**（盲批是信任线最危险的断裂）、**版本历史 + 回滚**（坏激活可恢复）、**词汇表浏览**（构造有据）、**EDN / schema 表单最小编辑器**（哑兜底必须在场）。刻意不内建的：可视化设计器、智能编辑辅助——扩展与 AI 渲染的地盘。大部分内建 UI 是免费的——meta 实体就是实体，现有渲染器直接渲染；必须专门造的只有**机械 diff**，它服从通道隔离铁律的加强版：

> **审批者看到的 diff，不能经过被审批者提供的任何渲染器。**

AI 摘要可以在旁参考，批准依据的正典是机械 diff——被告的陈述可以听，笔录必须自己看。三条完整性规则：内建不可卸载（恢复分区，不是默认分区）；扩展视图里的批准回链内建审查；内建随内核版本化（定义空间损坏时唯一完好的界面）。

#### 总原则：一座每层都能独立站住的塔

meta 实体最小核（删除测试）、UI 骨架（四判据）、meta 内建 UI（BIOS）——三刀是同一条规则的三次应用：

> **每一层都必须有一个不依赖上层的最小实现。** 内核不依赖 meta UI 就能跑；meta UI 不依赖 AI 就能用；应用不依赖 assistant 就完整；渲染不依赖生成就能看。每一层对上一层是增强，不是前提。

嵌套的降级路径：任何一层塌了，底下照常运转。第九层的 AI-optional 原则是这条规则的特例——智能只是塔的最高一层，不是承重墙。

## 第五部：下注与账目（第十一层 + 洞 + 自审）

*策略层、尚未解决的洞、闭环自审——主张之外，记下我们还欠什么。*

### 第十一层：策略——Agent-First，修订

agent-first 的底气来自两条路线的**不对称性**：Agent-first → AI-embedded 是"包装"问题（真相源已结构化，加一个内置消费者即可）；AI-embedded → Agent-consumable 是"重写"问题（流程知识埋在代码里从未被声明成数据，**从未被结构化记录的东西，无法事后廉价恢复**）。Agent-first 购买了一个期权，embedded-first 放弃了它。这与 wizard 的"延迟承诺"同构：无论走哪条路，底座都不浪费。

落地方位维持 v1：**企业内部员工工作台**。激励天然对齐（组织的 KPI 就是任务完成效率，应用方暴露结构没有利益冲突）；安全合规降级为常规 IT 治理——第八层把这句话正式化了：委托挂在员工身份上走既有 SSO 与 OAuth，确认门对接企业既有的审批文化与通知基建（IM、邮件、短信），**Agent 协作不需要新建任何权限设施，只需要接入已经跑了二十年的那一套**；高频事务（审批、报销、入离职、工单）恰是状态机友好的流程密集型场景；接入不需要重写存量（规范适配，先接三五个高频系统）。

**滩头中的滩头：运维。**一句"创建一个 2C4G 的虚拟机，ubuntu 系统，密码默认"走完全套机制：运维说完转身（约十秒认知成本，到此为止）；"2C4G"靠 schema options 的组织别名解码——组织的词汇表住在合同里，黑话不需要人类翻译官；"ubuntu"落到加固镜像默认值；没说的 region、VPC、安全组、计费被组织默认吸收——**没说的和说的一样重要，委托吸收的不只是劳动，是配置决策的疲劳**；"密码默认"解析为策略路由（vault capability 产密钥引用，密码不经过人手与 agent 上下文——暴露哪些字段决定了什么会泄漏）；guard 逐项求值（配额、预算、镜像合规）；花钱动作触发确认门，手机上一批——这是此人第二次也是最后一次认知投入；效果 spawn 云能力，job 异步、结果事件回流，虚拟机成为实体 `vm:i-abc123`，之后的"重启它""扩到 4C8G""删了重建"全在生命周期图上——**流程图就是 runbook 的机器可读形态**。运维之所以是最佳滩头：意图高频、黑话密集（知识压缩最狠）、高风险（钱与生产）、天然 runbook 形，且变更管理文化早已存在——确认门不是要教给运维的新东西，是他们已经在做的动作，只是从"填变更单"变成"点一次手机"。

### 尚未解决的洞：修订后的诚实清单

v1 列了五个洞。修订后：两个被部分填上（其一被填掉大半），四个仍在，新的洞随新平面打开。按严重程度排：

1. **安全与权限模型（v1 排第一；第八层已填掉大半，剩余收窄为三件事）**。委托模型、确认门、信道分离、渐进信任已成设计；真正剩下的：其一，**确认疲劳**的实证——分级和批量确认在纸面上成立，但人类会不会退化成橡皮章需要真实使用检验；其二，**范围配置的 UX**，决定采用率的产品问题；其三，提示注入被**有界化但未消除**——被攻陷的 Agent 仍能做委托范围内免确认的一切，且 meta 平面对注入有放大效应（恶意定义本身可以是注入载体），`_meta` 的审批 guard 因此不是可选项而是必需品。
2. **意图缺口（第九层已给机械解，实证未做）**。clarification 的对话记录挂在决策点上，就是意图注记——日志记"发生了什么"，transcript 记"怎么聊清楚的"。剩下的是工程与体验问题：引出门的触发时机（何时该问而非该猜）、对话收敛率、澄清再委托的信任校准。
3. **标准化卡位**。MCP Apps、A2UI、AG-UI、WebMCP 仍在快速演进。v2 与 function-calling 的分界因"作用域从超媒体继承"而更清晰，但独创性窗口可能只有一两年。
4. **表达力边界的实证**。已从"纯推断"升级为"一个 toy 验证"：状态机 + schema 吃下了向导、审核、CRUD、生命周期、跨流程导航；自由画布与多人协作依旧无解。
5. **零数据**。缓存分层省多少钱、sitemap 前缀命中率——仍然只有推理，没有测量。
6. **（新）定义迁移的实操**。版本戳、只增不删、激活前校验都是纸面设计——"在途实例遇上定义变更"的真实工程量，要等第二个真实应用来检验。
7. **（新）capability 沙箱的真实性**。JVM 沙箱弱，现实做法是受限解释器或独立 worker；不要假装 `eval` 加正则过滤等于安全。coding capability 的验证管道是内核里最贵的一段代码——何时值得，是投资判断不是技术判断。
8. **（新）双层日志的成本**。业务事件 + 定义事件 + capability 产物共用一条日志，重放与存储的成本模型未测量。
9. **（新）生成式渲染的信任边界**。binding-only（AI 选形式永不选数据）与交互元素必须 action 背书，目前是纸面防御——视觉注入通道的实测未做；渲染凝固策略（首次生成、之后稳定）的肌肉记忆收益未验证；机械 diff 面临 **diff 疲劳**——与确认疲劳同族的认知问题，大 diff 会被 skim，审批者的注意力是比渲染完整性更窄的瓶颈。

### 闭环自审：钢与粉笔

一份主张"把结构声明出来"的文档，欠读者一份对自身结构的诚实审计。结论：两个环闭上了，五个环还开着。

**闭上的环有两个。** 其一是**概念递归环**：全文每一层遇到新问题，答案都是同一套语法升一层——业务裁决用 guard，定义裁决还是 guard，高危审批仍在 guard 阶段，确认送达走 capability，人类批准是提议。权限层是最好的自证：拆到最后零个新概念，一个词汇表说完了所有平面的事。其二是**前五层的实证环**：论题 → 实现 → 调试教训 → 修订论题，这个回路真实跑过——"拒绝作为数据""目标相关性分层"都是实现倒灌回理论的，不是推演出来的。

**开着的环有五个。** 其一，六至十层只有论证闭环，没有实证闭环——本文档的权威来自第五层的实现，而实现只覆盖最终架构的一半。**这个环一段是钢，四段是粉笔**：定义迁移若在实践中不可行，第六层塌；沙箱真实性不达标，第七层的 coding capability 塌；引出门的收敛率与澄清再委托的校准失手，第九层的体验赌注塌；binding-only 防不住视觉注入，第十层塌。其二，经济主张零数据——工作台适配、"市场而非雇佣"、认知带宽乘法，整段没有一枚证据。其三，内核形状已从协议推导（动词决定词汇表），但"协议为何只有这些动词"仍是断言——固定点没有推导者，这一环可能永久开放。其四，**"让 AI 成为更快的 operator"是主张不是测量**：五座钟里只有可委托、可验证、构造即正确是结构性成立，墙钟、token 成本、长任务成功率一座没测；demo 的任务全是 1–6 步，短到分辨不出合同是帮助还是开销。其五，生成式渲染整层是纸面——绑定式渲染与 action 交互背书的注入防御未实测，渲染凝固策略未验证，机械 diff 面临 diff 疲劳（与确认疲劳同族的认知问题）。

**最深的一道开环在文档自身。** 按它自己的标准，一份关于自描述系统的文档，终点是被那个系统吸收：成为日志的创世块，它的每次修订是一条定义事件。现在它不是——它是 Markdown，站在它所描述的系统外面。本文不声称这一点（声称了就是修辞）；它成为事实的条件，与第六层的落地是同一个条件。

**把粉笔换成钢的路径是五条垂直切片，不是下一版文档：**

1. **确认门切片**——一次性穿过第七、八层的核心主张：agent 执行高危动作 → guard 挂起 → pending 实体化 → notification capability 送达 → 人类在推送上 approve → 事件留痕带 actor/principal。一个功能同时验证 guard 第三语义、确认实体、出站能力、委托模型四个论点，且全部复用前五层已验证的机器；
2. **最小 meta 切片**——flow 定义从源码常量挪进事件日志，加一个定义编辑流和一个激活 guard。"非法动作被拒绝、非法定义也应被拒绝"从原则变成测试用例；
3. **委托实体切片**——把 agent 执行从浏览器 Promise 链挪进引擎的流程实例：N 路并行、崩溃续跑、舰队队列页。验证"裁决器即并发控制"与"人类监控成本不随 N 超线性"两个论点；
4. **plan-exec 切片**——批量裁决计划，一次决策、机器速度执行。验证操作节奏与裁决权的分离；
5. **骨架与渲染切片**——widget 加画布、组件词汇表三五个、render capability（实体缓存 + 关注点 → 绑定说明），主页改造成态势投影（待处理 / 在飞 / 最近事件）。与确认门切片共享 pending 实体机制，收件箱顺带落地。验证 binding-only（模型发不出数字）与注入防御（合同外的按钮无法提交）两个论点。

做完这五条，剩下的粉笔只有内核的最后断言与经济数据——前者可能永远如此（不动者没有推导者），后者是测量问题。

## 结语：一个真相，两个站点，三个平面

整场论证的逻辑链是同一个原则的逐层展开：

> 两个锚点（人机共享同一套流程知识 · 为操作而写）→ 界面作为双边合同 → 解耦（应用归应用，助手归助手）→ 记忆归应用 → sitemap 静态化 → 状态机 + schema 实现 →（v2）定义即数据，应用编辑自己 →（v2）capability 即边界，应用触碰世界 →（v2）权限即委托与确认，人类留在环内 →（v2）交互即三扇门，人类只在判断与模糊处在场 →（v2）渲染即选择，形式可生成、数据永不发明，骨架与 BIOS 不委托。

原则浓缩为一句话：**把结构声明出来，把消费方式留到最后再定。** 而这句话的因，是引言里的两个锚点——知识只有一份，人机共读；软件为操作而写，代码只是副产品。全文的机制，都是这两个"为什么"的"怎么办"。

最终的画面：**一个真相（单引擎 + 单日志），两个站点（业务平面 + 定义平面），三个平面（业务、定义、能力），一套协议（带 schema 的实体、带 guard 的动作、可导航的链接），一套渲染器架构**（人类界面、确认推送、聊天窗，皆是同一架构的实例）——外加一条穿过三个平面的信任线：主语是委托，确认是消息，信任是数据。Agent 不是站在系统外面的神——它是 `_meta` 的一个租户、合同的一个客户端、能力的一个使用者，和所有其他参与者一样受同一套裁决约束；它的每一次高危动作，都要敲一敲你的手机。

CLI 给 Agent 工具，Skill 给 Agent 知识，UI 给 Agent 处境。而 v2 往前再走了一步：当处境本身成为数据，应用第一次有能力讲述自己；当交互被收口为边界，应用第一次可以安全地触碰世界。

界面一直是写给人类的文档。v1 说，是时候让它同时成为写给机器的协议。v2 补上后半句：**当协议足够诚实，应用就能用这份协议编辑自己——并在治理之下，伸出手去。**

而这份文档自己，是那块基石的草图：在定义平面存在之前，它只是一份描述；在之后，它的每一次修订，都会成为那条日志里的一条定义事件。

## 附录 A：`_meta` 实体规格（图纸）

> 本附录是第六层的图纸化：实体目录、schema 与操作。它仍是粉笔——但没有图纸的粉笔和有图纸的粉笔，施工难度是两回事。

### A.0 什么够格成为 meta 实体

三个测试，全过才入 `_meta`：

1. **结构而非实例**：它定义"应用是什么"，不是"应用此刻在哪"。在途状态、确认请求、capability 运行（job）都是实例，留在业务平面；
2. **定义速度**：它的变更应当以版本为单位发生，走"草稿 → 校验 → 激活"，而不是即时执行；
3. **被按名引用**：它的名字会出现在其他定义的数据里（guard 名、flow 名、capability 名、资源类型名）。

事件日志是共享底座，不属任何平面。

### A.1 实体目录（九个顶层 rel）

| rel | 种类 | 定义什么 | 读写 |
|---|---|---|---|
| `meta/flows` | 定义 | 行为结构：流程状态机（节点/字段/动作/边） | 可写（经激活） |
| `meta/resources` | 定义 | 数据结构：资源类型（存储集合、键、href 模式、生命周期绑定） | 可写 |
| `meta/projections` | 定义 | 呈现结构：投影模板（collection / dashboard / item） | 可写 |
| `meta/capabilities` | 能力 | 外联行为：kind（转换/提取/效应）、输入输出 schema、宿主、成本档 | 可写 |
| `meta/activations` | 治理 | 激活队列——definition-lifecycle 的实例空间 | 可写 |
| `meta/versions` | 治理 | 不可变版本工件（内容寻址） | 只读（由激活产生） |
| `meta/policies` | 治理 | 委托与确认策略（scope、确认阈值、渐进信任账本） | 可写 |
| `meta/registries` | 词汇 | 内核词汇表：谓词 / 效果 / 类型 / kind 清单 | 只读 |
| `meta/self` | 词汇 | 自举种子：definition-lifecycle 自身的定义 + 种子 guard 集 | 只读 |

目录与第六层的推导对齐：前三行是三个内环动词所需的结构（迁移要 flow、呈现要 projection、裁决要 guard 声明——挂在 flow 的 action 上）；capabilities 对应第四个动词"触达"；治理三行是信任线在定义平面的落点。

#### A.1.1 减法：最小核与扩展次序

九个 rel 是**终点目录，不是起步清单**。按"简单，但不能再简单"做一次减法，最小核只有四个：

| 核心 rel | 砍掉的失败模式 |
|---|---|
| `meta/flows` | 定义不是数据，回到改源码——没有 meta |
| `meta/activations` | 定义变更绕过裁决——"非法定义也被拒绝"的对称性破掉；meta 沦为绕过权限的后门，**比没有更糟**（给了 Agent 写权限，却没有审批） |
| `meta/registries` | Agent 只能猜 guard 名，反复提交反复被拒——词汇表是构造合法定义的前提（且零成本：内核已有，只是暴露） |
| `meta/self` | lifecycle 自身不可读，Agent 不知道激活流程长什么样——读不了就操作不了 |

简单性的判据不是实体数量，而是**删除测试**：每个不可删除的元素，删掉它都会破坏一条已命名的性质。上面四个全过，第五个砍不动了。

其余五个各有明确的到来时机，不提前建：

- `meta/resources`——第一个"全新资源类型"的需求出现时（比如加书签）；
- `meta/projections`——第二次为新流程手写 entity builder 时；
- `meta/capabilities`——应用第一次需要出站调用时（第一个是 notify，它顺便服务确认门切片）；
- `meta/policies`——assistant 真的带着 principal 行走时（确认阈值可先硬编码）；
- `meta/versions`——严格说不是实体而是日志的视图：激活事件本身就是版本记录，内容寻址的工件是它的属性。

最小核的全部行为 = **一台状态机（definition-lifecycle）+ 一排编辑动词 + 一组不变式 guard**。不是框架，不是插件系统——一张会长大的表格，和一道不委托的审批门。"闭环自审"里的最小 meta 切片，施工范围就是这个最小核。

### A.2 关键实体 schema（Siren 示例）

**flow 定义**——注意它的递归性：字段定义本身就是字段，动作定义本身就是动作：

```json
{
  "class": ["meta", "flow-definition"],
  "properties": { "name": "post-status", "version": 3, "status": "active",
                  "initial": "draft", "terminal": ["archived"] },
  "entities": [{
    "class": ["meta", "node-definition"], "rel": ["node"],
    "properties": { "name": "published", "title": "已发布" },
    "entities": [{
      "class": ["meta", "action-definition"],
      "properties": { "name": "archive", "title": "归档", "method": "POST",
                      "to": "archived", "guards": [],
                      "requires-confirmation": "high",
                      "effect": { "type": "transition" } }
    }]
  }],
  "actions": [
    { "name": "revise",    "title": "修订（开新草稿）", "guards": ["is-active"] },
    { "name": "deprecate", "title": "废弃", "guards": ["no-live-instances"] }
  ],
  "links": [{ "rel": ["self"], "href": "/_meta/api/entity?rel=meta/flow:post-status" },
            { "rel": ["versions"], "href": "/_meta/api/entity?rel=meta/versions&of=flow:post-status" }]
}
```

`effect` 字段是第七层的接线点：纯效果 `{"type": "transition"}`，能力效果 `{"type": "spawn", "capability": "summarize", "bind": {...}, "on-done": "summarized"}`。`requires-confirmation` 是第八层的风险标注。**定义定义的语言，就是被定义的那套语言**——这是自举在 schema 层的体现。

**字段语义轴（第九层）**——field-definition 在 name / type / constraints 之外，必须声明值的来源与交互语义：

```json
{ "name": "region", "type": "select",
  "semantics": "org-standard",
  "source": { "kind": "context", "from": "project.homeRegion" } }

{ "name": "content", "type": "textarea", "required": true,
  "semantics": "work-product",
  "source": { "kind": "proposal", "capability": "draft", "options": 3,
              "selection": "human-required" } }

{ "name": "subnet", "type": "select",
  "semantics": "elicitation",
  "on-invalid": "clarify",
  "elicit": { "strategy": "options-first", "max-turns": 5, "timeout": "72h" } }
```

四种语义（org-standard / intent / work-product / elicitation）对应六种来源（默认四态——静态、上下文、策略路由、词汇别名；显式意图；起草+选择；引出；查找；效果产出）。默认值由引擎在 exec 时对未指定字段应用、guard 对最终参数求值，日志记录参数出处（default / intent / proposal / elicited），确认消息据此渲染"哪些是说的、哪些是被假设的"。

### A.3 操作：定义的编辑动词

草稿态 flow 定义上的动作（全部过三层裁决，与业务动作同一台机器）：

| 动作 | 字段 | guard |
|---|---|---|
| `add-node` | name, title | is-draft, node-not-exists |
| `add-field` | node, name, type, required, constraints | is-draft, node-exists, type-registered |
| `add-action` | node, name, to, guards[], fields[], requires-confirmation?, effect? | is-draft, node-exists, to-exists, guards-registered, effect-known |
| `remove-node / field / action` | … | is-draft, not-referenced |
| `submit` | — | is-draft（进入 definition-lifecycle） |
| `revise` | — | is-active（产生 v+1 草稿） |
| `deprecate` | — | no-live-instances |

resource / projection / capability 定义各有对称的动词集（`add-resource`、`bind-lifecycle`、`set-projection`、`register-capability`……），形态相同：草稿编辑 + submit + 激活，不逐一列举。

### A.4 definition-lifecycle（meta flow 本体）

```
draft --submit--> validating
validating --checks-pass--> pending-approval
validating --checks-fail--> draft（附校验报告）
pending-approval --approve--> active（写 versions，重生成 sitemap，bump :version）
pending-approval --reject--> rejected（reason 入日志）
pending-approval --timeout--> expired（时钟 capability 的 tick 提议）
active --revise--> draft（v+1）
active --deprecate--> deprecated
```

`approve` 的 guard 永远要求 `actor-is-human`：**定义变更的裁决权不进入渐进信任的白名单**——assistant 可以提议一切，批准权不可委托。

### A.5 激活的不变式（注册在种子 guard 集里）

- `edge-targets-exist`：每条边的目标节点存在；
- `guards-registered` / `field-types-known` / `effect-known` / `capability-registered`：引用皆可解析；
- `initial-exists` + `terminal-reachable`：图的基本健康；
- `resource-href-unique`：路由无冲突；
- `projection-refs-valid`：投影引用的资源类型存在；
- `capability-schema-compatible`：spawn 的 bind 与能力输入 schema 相容；
- `no-live-instances-on-removed-nodes`：激活时点无在途实例踩在被删结构上；
- `field-source-declared`：事实型字段必须声明来源（默认 / 查找 / 引出 / 效果产出），不得悬空等 agent 猜——事实永不发明；
- `work-product-selection-gated`：价值载体字段必须携带 human-required 选择声明，exec 时 guard 检查选择事件存在。

这份清单本身就是"非法动作被拒绝、非法定义也应被拒绝"的测试用例目录。

### A.6 `_meta` 的权限平面

- **读**：已认证 principal 皆可——agent 要构造定义，必须能读词汇表；
- **草稿编辑**：human-admin | meta-agent；
- **approve**：`actor-is-human` 且有 mandate；
- 整站挂在 `_meta` 前缀：鉴权、限流、审计单点收口。

### A.7 自举与引用

`meta/self` 是内核里唯一硬编码的定义集合：definition-lifecycle 的定义本身 + 种子 guard 集。它只读——内核可读不可写，内核以下皆可写。业务平面与定义平面的连接保持在链接层：业务实体的 links 可携带 `_meta` 完整路径（客户端零改动跨站），业务站的导航枚举排除 `_meta`——进入定义层，必须是显式意图。

### A.8 内建 UI（BIOS）

`_meta` 必须自带最小 UI：**随内核发行、不作为定义存在日志里、挂在扩展无法劫持的保留路由下**——自修改系统的修理工具不能住在被修改的部分里（完整论证见第十层）。最小集与最小核一一对应：

| 内建面 | 服务于 | 必须内建的理由 |
|---|---|---|
| 定义查看 | `meta/flows` | 自省不致失明——不知道激活的是什么就无法判断一切 |
| 激活队列 + 机械 diff + approve/reject | `meta/activations` | 盲批是信任线最危险的断裂；diff 渲染路径零 AI 零扩展 |
| 版本历史 + 回滚 | `meta/versions` | 坏激活可恢复——自愈能力 |
| 词汇表浏览 | `meta/registries` | 构造定义时有据可查 |
| EDN / schema 表单最小编辑器 | 草稿编辑 | 哑兜底必须在场：meta 实体就是实体，标准渲染器直接可用 |

刻意不内建：可视化流程设计器、智能编辑辅助——那是扩展与 AI 渲染的地盘。完整性三条：内建不可卸载（恢复分区，不是默认分区）；扩展视图里的批准回链内建审查——**审批者看到的 diff 不能经过被审批者提供的任何渲染器**；内建随内核版本化，定义空间损坏时它是唯一完好的界面。

## 修订史

**v2（初版）**：对 v1 的修订。契机有二：其一，v1 的核心主张已用 Clojure/ClojureScript 做成可运行的全栈实现，并通过浏览器端到端验证——若干论点从推断升级为事实，调试过程也暴露了论证没预料到的问题；其二，围绕"定义即数据"的推演，把架构从一份合同扩展为两个站点、三个平面。

主要变化：

- 第一至四层保留 v1 论证（收敛了篇幅），补入实现侧的印证；
- 第五层重写：以实测证据取代选型推理，并收入调试教给我们的东西——目标相关性、拒绝作为数据、裁决层与自由度的解耦；
- 新增第六层（定义平面：meta application 与 `_meta` 站点）、第七层（能力平面：capability 作为与真实世界的边界）；
- 新增第八层（权限：委托、确认与渐进信任——复用 Web 2.0 的主语模型，关键动作的确认门以通知为载体），原策略层移至第九层；
- "尚未解决的洞"相应修订：v1 排第一的安全与权限洞被第八层填上大半，新的洞随新平面打开。

**v2.1（自审轮）**：对文档本身做了一次闭环审计并据此修订——内核的形状从断言改为推导（注册表是协议动词的镜像）；显式修正 guard 概念在权限层的伸展（状态谓词 vs 策略标注）；新增"闭环自审"一节，标注哪些环是钢（已实证）、哪些是粉笔（仅论证），并给出把粉笔换成钢的两条垂直切片；结语补上文档自身的创世块定位。

**v2.2（图纸轮）**：新增附录 A——`_meta` 的实体规格：九个顶层 rel 的目录与准入测试、最小核与扩展次序（A.1.1，删除测试证明砍不到四个以下）、关键实体的 Siren schema、定义的编辑动词、definition-lifecycle 状态机、激活不变式清单与 `_meta` 的权限平面。仍是设计，但把粉笔描成了图纸。

**v2.3（锚点轮）**：引言重排——从两个锚点出发（人类与 AI 面对同一套业务流程，共享同一套业务流程知识；不是为了让 AI 更快地写代码构建软件，而是为了让 AI 能够更好地操作软件而写软件），原机制论述收拢为"从锚点到合同"一节；结语的逻辑链以锚点为起点，并回扣收口。机制之前，先立为什么。

**v2.4（交互轮）**：新增第九层"交互——三扇门、字段语义与澄清器官"（确认门之外补齐选择门与引出门；字段语义轴与值来源六分格、事实永不发明；交互成本阶梯；clarify 作为内嵌器官的 capability 合同、runner 阶梯与 AI-optional 总原则；澄清再委托；委托即流程实体与 plan-exec），原策略层移至第十层并补运维走查；引言锚点二补"认知带宽乘法"的定义、行业盲区三道锁与 UX 目标倒转；第五层补 demo 自我批判；洞清单 #2 改为"设计已补、实证未做"；闭环自审增至四条垂直切片；附录 A 的 field-definition 补语义轴。

**v2.5（渲染轮）**：新增第十层"渲染——形式可生成，骨架与 BIOS 不可"（生成式渲染：AI 选形式永不选数据、绑定式渲染、交互必须 action 背书、按关注点凝固；骨架五面与四判据；`_meta` 内建 UI 的 BIOS 原则与机械 diff 的通道隔离；总原则"每一层都有不依赖上层的最小实现"），原策略层移至第十一层；闭环自审增至五环五切片；洞清单新增生成式渲染的信任边界与 diff 疲劳；附录 A 补 A.8 内建 UI。

**v2.6（重排版）**：内容零改动，只动组织——新增导览（五部地图与两条阅读路径）；十一层按逻辑分组为五部（层号保留，交叉引用不变）；v2–v2.5 的修订说明从开篇下沉为文末"修订史"。
