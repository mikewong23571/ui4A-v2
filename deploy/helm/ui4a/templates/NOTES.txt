UI4A v0.1.0-experimental.1 renders as a single-replica, non-HA stack.

Before installing, create these server-owned inputs in namespace {{ .Values.namespace.name }}:

1. Secret {{ .Values.secrets.existingSecretName }} containing the canonical production
   deployment JSON under key ui4a-deployment-secrets plus the individual state-service credential
   keys named by deploy/postgres/deployment-bindings.json. Secret values must never be placed in
   values.yaml or rendered evidence.
2. ConfigMap ui4a-deployment-settings with key settings.json sourced from the canonical validated
   production settings.
3. ConfigMap ui4a-postgres-bootstrap with key bootstrap-roles.sql sourced from
   deploy/postgres/bootstrap-roles.sql.
4. ConfigMaps ui4a-temporal-static and ui4a-temporal-dynamic with key docker.yaml sourced from
   deploy/compose/temporal-config.yaml and deploy/compose/temporal-dynamicconfig.yaml.
5. ConfigMap ui4a-realm-import with key realm-import.json sourced from
   deploy/keycloak/realm-import.json.
6. External ConfigMap ui4a-panel-ca with key ca.crt containing the trusted Panel root CA. The chart
   references this ConfigMap but never renders its certificate material.
7. The retained pki-data volume populated with root-ca.crt and PostgreSQL server.crt/server.key;
   the database certificate must cover the configured PostgreSQL service hostname.
8. TLS credential Secret {{ .Values.istio.tlsCredentialName }} in the ingress gateway's configured
   credential namespace.

Replace every example image digest, hostname and StorageClass (or select explicit static retained
volumes) before installation. The environment-specific overlay owns those facts.

Completed bootstrap Jobs are intentionally retained: replacement Pods use their durable Complete
conditions as restart gates. An upgrade runbook must delete and recreate only the explicitly rerun
Jobs after taking its pre-upgrade backup.

The v0.1 automatic CronJob is suspended by default. Its retained single-database command is an
incomplete, non-authoritative fixture and must not be unsuspended or used as recovery evidence. The
only verified recovery path is the host-operated, quiesced ten-artifact workflow governed by
scripts/t22-k8s-recovery-live.ts; it covers four databases, runtime/workspaces, realm/config refs,
deployment Secret archival and runtime PKI with checksums, an atomic completed manifest, isolated
restore, projection rebuild, and authority/identity/Run evidence.
